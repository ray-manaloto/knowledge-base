## FINDINGS

### P1 — Chunk-level `captured_at` max can misorder supersession for a mixed-source chunk
`python/src/kb_setup/chunks.py:356-377` (docstring + `return sorted(...)` at :377)

`chunk_captured_at()` (chunks.py:338-353) takes the **max `captured_at` across every node in the
file**, and `replay_order()` (chunks.py:356-377) sorts whole chunk files by that single value, oldest
first, relying on "last chunk to name a `source_file` wins" in `build_merge`. `assemble()`
(chunks.py, confirmed by reading it directly) accepts an arbitrary list of chunk-file paths with no
constraint that they share one `capturedAt` — so a single assembled chunk CAN legitimately mix a
freshly-extracted `source_file` A with a stale, previously-cached `source_file` B (e.g. a partial
re-run that only refreshed some of a batch). If it does, the chunk's mixed-max date is pulled up by A
and the whole file — including its stale B nodes — replays LAST, so the stale B silently overrides a
separately-committed, genuinely newer B chunk. Per-file date is not the same question as
per-`source_file` recency, and only the former is checked.
Verified: `assemble()`'s signature takes `chunk_paths: list[Path]` with no per-source uniformity
check; `kb-extract.js`'s `capturedAt` is one value per fan-out call, so cross-batch mixing is exactly
what would trigger this. Narrow but real — genuinely confirmed, not refuted.

### P1 — The clone-relative rename orphans pre-existing basename-keyed nodes (verified LIVE in this repo, not just theoretically)
`.claude/workflows/kb-extract.js:106-124` (the `sourceFileFor` helper)

`source_file` identity switches from bare basename (`hooks.md`) to clone-relative path
(`docs/claude-code/hooks.md`). Supersession in `build_merge` is exact-string-keyed on `source_file`
(confirmed: `graph.py`'s merge logic, cited by codex at `graph.py:1156-1165`), so nodes still on the
OLD basename scheme are never touched by a chunk emitted on the NEW scheme — they neither get pruned
nor superseded, they just sit in the graph forever alongside the fresh copy.

**This is not hypothetical — I confirmed it is already the corpus's live state.** This commit
rewrote `sources/extractions/claude-code-docs-2026-08-05-refresh-docs.json` (271 `source_file` fields,
`hooks.md`→`docs/claude-code/hooks.md`) but did **not** touch the older, still-committed
`sources/extractions/goal-engineering-docs.json`, which still carries 13 nodes with the bare
`"source_file": "hooks.md"` (ids prefixed `ccgoal_...`). Those 13 ids have **zero overlap** with the
69 fresh `claude-code-hooks_...` ids in the rewritten chunk. Both sets will coexist in the graph after
the next `kb-build`/`kb-merge`, and nothing in the current scheme will ever again make the stale
13-node copy get pruned, since its `source_file` string no longer matches anything else in the corpus.
The very fix meant to make supersession deterministic has stranded old-scheme data undead.

### P2 — `captured_at` is validated for presence only, not format, before being used as a sort key
`python/src/kb_setup/chunks.py:108-110` (the presence-only check) feeding `chunks.py:338-353`
(`chunk_captured_at`, used by `replay_order` at :377)

`_node_issues` (chunks.py:93-119) only checks `missing = [k for k in _NODE_REQUIRED if k not in n]`
(line 108) — it never validates that `captured_at` parses as a real ISO date. `chunk_captured_at`
then does a plain lexical `max()` over the raw string values (chunks.py:352). A node with
`captured_at: "zzz"` (or any string that lexically sorts after real `YYYY-MM-DD` values) passes
validation cleanly and would make its whole chunk sort LAST in `replay_order`, incorrectly "winning"
supersession for every `source_file` it touches — even against chunks with legitimately newer,
well-formed dates. Confirmed both cited spans match exactly.

### P2 — The graph-writer version gate blocks docs-only updates that never touch graphify
`python/src/kb_setup/cli.py:48-57` (the `_GRAPH_WRITERS` gate) vs. `python/src/kb_setup/graph.py:1471-1480`
(`update()`'s docs branch)

`cli.py` runs `graphify_env.assert_pinned_graphify(repo_root)` (which `raise SystemExit`s on a
version mismatch — confirmed at `graphify_env.py:261-268`) for **every** `update` invocation, before
it knows which source (or which mix of sources, for a bare `kb-setup update`) is being targeted. But
`graph.update()` branches a `kind == "docs"` source straight to `_advance_docs_pin` (graph.py:1479-
1480), which is pure `git diff --name-status` — confirmed by reading `_advance_docs_pin`
(graph.py:1536-1583) top to bottom: it never calls `graphify_exe()` or spawns any graphify subprocess.
So a stale graphify install now aborts a docs-mirror pin advance that never needed graphify at all —
the gate is scoped to the subcommand category, not to whether the specific run will actually invoke
the pinned binary. This is a genuine round-2 catch on round 1's own fix (the writer-gate feature is
entirely new in this commit, added in response to the prior cold-lane P1 about a stale binary
silently destroying hyperedges).
