## What a function hook IS, mechanically (from `mods/README.md` + `mods/sec-default/`)

Source: `https://raw.githubusercontent.com/anthropics/claude-code/main/mods/README.md` and `mods/sec-default/{README.md,hooks/{hooks.json,register.ts,index.ts}}` (fetched 2026-09-10, `main` branch, no pinned SHA — this is a live/moving target, see Stability section).

- **A "mod" = a Claude Code plugin whose behaviour lives in a hooks module**: one `register(on, options)` entry point that hooks the engine's events as **TypeScript functions** shaped `($, e, next) => ...`. `mods/README.md`: *"one `register(on, options)` entry that hooks the engine's events as functions (`$`, `e`, `next`)."*
- **Declared like an ordinary plugin, but with a `hooks/hooks.json` naming the module(s):** `mods/sec-default/hooks/hooks.json` = `{"description": "...", "modules": ["./register.ts"]}`. Plugin folder shape: `.claude-plugin/plugin.json` (ordinary plugin manifest — name/version/description/author) + `hooks/hooks.json` (points at TS module(s)) + the TS itself, typed against declarations `/plugin-types` writes (`import type { On } from 'claude-code'`).
- **Composition model is middleware/Express-style, by registration order**: `on(eventName, ($, e, next) => ...)`. `next(e)` continues the chain; `next.to(e, "append")` jumps straight to a named TIER (see below) skipping intervening tiers; returning `{ deny: <reason> }` from a hook DENIES the event outright (`sec-default` denies `tool.register` this way, returning `{ deny: TOOL_REGISTER_REFUSAL }`).
- **A "tier" is the enforcement seating structure — this is the key enforcement primitive.** From `sec-default/README.md`: plugins sit in three tiers — **`prepend`** (organization-installed, seated first/outermost), **`user`** (a person's own installed plugins, seated in the middle), **`append`** (organization-installed, seated last/innermost — i.e. closest to the actual engine behavior). `next.to(e, "append")` — jumping straight to the append tier — is how `sec-default` makes the organization's classic hooks, prompt content, settings and tool policy **unreachable by a user-tier plugin**, because a user-tier hook in the chain never gets the chance to intercept before `sec-default` forwards the event past it. **This is the mechanism-level answer to "can a plugin be made non-skippable by a lower-privileged actor": yes, by seating a hook in the `prepend` tier and calling `next.to(e, "append")` to bypass every `user`-tier hook on specific named events.**
- **Refusal is per-event, typed, returned as data, not thrown**: `{ deny: <string-or-object-reason> }`. `sec-default` refuses `tool.register` from a `user`-tier caller when `Policy.hasMcpAllowlist` is true (an MCP allowlist is configured in managed settings at all, even if empty) — i.e. **the mere presence of an MCP-server allowlist in managed/org settings is what triggers the refusal of unlisted user-registered MCP tools**, not membership in the list itself being checked per-tool here (that check happens elsewhere; this hook's job is only "is there a policy governing this at all").
- **Fails closed**: `sec-default/README.md`, verbatim: *"policy is read through `$.settings.read({ source: 'policy' })`, one read serving a burst; both fail closed, so an unreadable policy counts as a policy in force."* An error reading policy does NOT open the gate — the safe default is deny/lockdown, not pass-through.
- **`$` is the sigil for the injected capability object** — an "effect-parameterized" interface handed to every hook, described in the original issue as tracked for side-effects ("safe through side-effect tracking over a parameterized `$` object"). Concretely (from the `diff`/`telemetry`/`sec-default` sources): `$.settings.read(...)`, `$.session.authorize()`, `$.session.id`, `$.session.model`, `$.http.fetch`, `$.env.get`, `$.fs.read/list/stat`, `$.process.run`, `$.store.get/set`, `$.clock.*`, `$.ui.*`, `$.command.register`, `$.telemetry.log/mark` (added by the `telemetry` mod itself via the `engine.create` event, meaning **later hooks in the chain can literally extend the `$` interface other hooks receive** — the `telemetry` mod's `engine.create` hook does `{ ...await next(e), telemetry }`).
- **`e` is the event payload** and carries **provenance**: `e.provider` and `next.origin.tier` identify which tier/plugin the event's subject came from — this is how `sec-default` distinguishes "an org-installed MCP server registering a tool" from "a user's own plugin registering a tool" and treats them differently on the SAME event type.
- **Admin/org control over what a plugin CAN do**: the original issue body states admins can "remove affordances from `$`" so that plugins beneath cannot invoke that side-effect at all — narrower than a permission prompt; it is removing the capability from the object itself before a lower-tier hook ever runs.
- **An event catch-all exists**: a single hook on `"*"` sees every event, including every other plugin's own calls on `$` — described in the issue as enabling "an audit log is one function."
- **`event` inventory observed directly in shipped source** (not exhaustive — this is only what the three built-in mods' READMEs happen to touch): `classic.*` (bridges to the OLD `settings.json`-style command hooks — see below), `prompt.section`, `prompt.context`, `skill.prompt`, `attribution.text`, `settings.read`, `tool.describe`, `command.describe`, `agent.offer`, `agent.spawn`, `tool.register`, `tool.list`, `tool.call`, `tool.check`, `command.run`, `command.register`, `session.*` (`session.start` observed), `ui.*` (`ui.render`, `ui.open/close/invalidate/log/resolve/status` observed), `fs.*`, `http.fetch`, `process.run`, `store.*`, `clock.*`, `model.*`, `mcp.call`, `audio.*`, `agent.list`, `engine.create`, `prompt.submit`, `turn.*` (`turn.complete` observed).
- **`classic.*` is the seam to the EXISTING settings.json hook system.** `sec-default` hooks `classic.*` and simply `next.to(e, "append")`s it — meaning the old PreToolUse/PostToolUse/etc. hooks this repo already relies on are themselves represented as one or more function-hook events (`classic.*`) inside the new engine, and a function hook can intercept/observe/forward them. This is the load-bearing fact for how the two systems relate: **function hooks are not a replacement that discards `settings.json` hooks; they are a strictly more general engine that the classic hook system is now internally routed through as one event family.**

## The full inventory of Claude Code enforcement surfaces (installed 2.1.267)

All of the below is **already fully ingested in this repo's own corpus** (`sources/claude-code-docs.manifest`, files under `sources/claude-code-docs/content/en/docs/claude-code/`) and is the STABLE, currently-shipping surface — distinct from function hooks/Mods above, which are pre-release.

- **Hook events** (`sources/claude-code-docs/content/en/docs/claude-code/hooks.md:1085-3397`, one `###` heading per event): `SessionStart`, `Setup`, `InstructionsLoaded`, `UserPromptSubmit`, `UserPromptExpansion`, `MessageDisplay`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `PermissionDenied`, `Notification`, `SubagentStart`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `Stop`, `StopFailure`, `TeammateIdle`, `ConfigChange`, `CwdChanged`, `DirectoryAdded`, `FileChanged`, `WorktreeCreate`, `WorktreeRemove`, `PreCompact`, `PostCompact`, `PreModelSwitch`, `PostModelSwitch`, `SessionEnd`, `Elicitation`, `ElicitationResult` — 32 distinct lifecycle events, the shape already used by this repo's own `PreToolUse`/`SessionStart`/`SessionEnd` hooks in `.claude/settings.json`.
- **`permissionDecision` semantics** (`hooks-guide.md:633-641`): on `PreToolUse`, `"allow"` skips the interactive prompt (enterprise deny/ask lists and MCP `requiresUserInteraction` still apply on top), `"deny"` cancels the call and feeds the reason back to Claude, `"ask"` shows the normal prompt, `"defer"` (headless `-p` mode only) preserves the call for an Agent SDK wrapper to resume. `PreModelSwitch` reuses the same field for allow/deny/ask-as-confirm. Other events use different shapes: `PostToolUse`/`Stop` use a top-level `decision: "block"`; `PermissionRequest` uses `hookSpecificOutput.decision.behavior`; `UserPromptSubmit` uses `hookSpecificOutput.additionalContext` (silently ignored if placed at the top level instead of nested — a real footgun).
- **A hook CAN block a non-Bash tool.** `hooks.md:1540-1543`: PreToolUse "Matches on any tool name except `EndConversation`" — explicitly including `Edit`, `Write`, `Read`, `Glob`, `Grep`, `Agent`, `Workflow`, `WebFetch`, `WebSearch`, `AskUserQuestion`, `ExitPlanMode`, and any MCP tool. This directly contradicts the standing memory-file risk this repo already tracks (`shell-edits-bypass-the-type-checker.md`, #671) about **shell-level file edits (e.g. `perl -pi`) bypassing a matcher scoped only to `Bash|Grep`** — the tool itself CAN match `Edit`/`Write`; a gap here is a matcher SCOPE choice in `.claude/settings.json`, not a platform limitation. (Corroborates rather than duplicates that memory — cited so a design pass doesn't re-derive it.)
- **PreToolUse runs before permission-mode checks, in EVERY mode including `bypassPermissions`** (`hooks-guide.md:963-967`, verbatim): *"A hook that returns `permissionDecision: 'deny'` blocks the tool even in `bypassPermissions` mode or with `--dangerously-skip-permissions`. This lets you enforce policy that users can't bypass by changing their permission mode."* This is the single strongest "non-skippable" primitive in the currently-shipping (non-experimental) surface.
- **`allowManagedHooksOnly`** (`settings-reference.md:3656-3675`, scope: **Managed only** — cannot be set from this repo's project-scoped `.claude/settings.json`): when true, ONLY managed-settings hooks + Agent SDK in-process hooks + explicitly force-enabled managed-plugin hooks run; "user, project, and local hooks, hooks from other plugins, and hooks declared in agent frontmatter" are all blocked outright, and `/goal` refuses to run while it is set (`settings-reference.md:3679`, paraphrased at the section end). This is the platform's own answer to "stop a lower-privileged actor from disabling or overriding an enforcement hook" — but it requires organization-level managed settings, which is out of this repo's reach per `do-not.md` (project-scoped only).
- **`disableAllHooks`** (`settings-reference.md:3679-3697`): scope `Any file`, but "Only managed settings can disable managed hooks" — i.e. a project-scoped `.claude/settings.json` CAN set `disableAllHooks: true` and it silently disables THIS repo's own guard stack (a real self-sabotage risk worth naming for the design lane), while a managed-settings `disableAllHooks` is stronger and also disables Agent SDK hooks unless a version-gated managed override is present.
- **Skills, output styles, and settings.json permissions are NOT independent enforcement mechanisms — they are prose/config the model reads, not code the platform runs.** Nothing in the fetched docs shows a skill or an output style able to DENY a tool call the way a `PreToolUse` hook can; both are advisory context. `permissions` in `settings.json` (allow/deny/ask rules) IS a real, code-enforced gate (checked in the same code path `permissionDecision: "allow"` explicitly says it does not override — "Deny and ask rules... still apply"), and is the one config-only (non-hook) enforcement surface that is genuinely non-skippable by the model, though a user with write access to `.claude/settings.local.json` can still weaken it at a lower scope than managed.
- **Stability marker for the whole stack**: none of the above 32 events, `permissionDecision` values, or the two `settings-reference.md` keys cited above carry an "experimental"/"early access" label in the fetched docs — this is the STABLE hook surface, in contrast to function hooks/Mods which `mods/README.md` explicitly marks "Early access."

- **The single most important NEW fact from this source, and it cuts against a naive "function hooks = non-skippable" reading**: *"a hook that fails (throws, overruns its budget, answers a wrong shape) is skipped."* **This is an ENGINE-level failure mode, and it is "skip", not "fail closed."** It does not contradict `sec-default`'s own fail-closed POLICY-read behavior (`Policy.decidedByPolicy`/`$.settings.read` catching and defaulting to lockdown is application code the hook author wrote); it means the ENGINE itself, when a hook's code errors or times out, routes around that hook rather than halting the whole event or denying by default. **This is a load-bearing fact for the enforcement design the advisor will build on**: a `prepend`-tier enforcement hook that throws on bad input is silently bypassed, not a hard stop — so "seat it in prepend and call next.to" is necessary but plausibly not sufficient without also making the hook itself defensive (fail-closed like `sec-default` chooses to be, by catching and denying rather than throwing).

Also states, consistent with the GitHub issue's own framing, that this is *"not a shipped Claude Code feature... an internal Anthropic proposal published as a GitHub issue on September 3, 2026"* and *"There is no documentation on code.claude.com"* (consistent with this report's own CHANGELOG control-arm finding of zero official mentions through 2.1.267).
- **One NEW concrete example set worth recording**: ten example hooks across categories — security (block destructive commands, redact secrets, guard protected paths), productivity (npm-to-pnpm rewriter, WebFetch cache), observability (audit log), UI (timing badge), integrations (WebSearch-to-Exa), and enterprise (capability lockdown). Consistent in kind with `sec-default`'s and the issue's own "a hook that says no" framing, but these ten are third-party-authored illustrative examples, not shipped Anthropic code — do not treat them as confirmed built-ins alongside `sec-default`/`diff`/`telemetry`.
- **A genuine, checkable DISAGREEMENT: version number.** The blog claims *"The feature exists in Claude Code binary version **2.1.266**, verified through binary analysis."* **This was independently checked against a REAL primary source this session — the actual installed Claude Code binary — and the claim does not hold as stated:**
  - `strings -a` against `/Users/rmanaloto/.local/share/mise/installs/npm-anthropic-ai-claude-code/2.1.251/node_modules/@anthropic-ai/claude-code-darwin-arm64/claude` (a real, locally mise-installed Claude Code binary, confirmed **version 2.1.251** via its `package.json`) found the function-hooks machinery **already compiled in**, five versions before the blog's claimed 2.1.266: literal strings `plugin_function_hooks_worker`, `plugin_function_hooks_load`, `plugin_function_hooks_register_tool`, `sec-default`, `plugin-types`, and runtime error/log strings `"function hooks are off for this session: the hooks worker crashed"`, `"hooks worker: respawning for "`, `"hooks worker spawned (one for every plugin)"`, `". Function hooks should only be used in REPL context (Stop hooks)."`, `"Internal error: function hook executed outside REPL context"`.
  - **Control arm**: the same `strings` pass, grepped for the pattern `CLAUDE_CODE_ENABLE_[A-Z_]*`, found **23 real, distinct flags** in this exact binary (`CLAUDE_CODE_ENABLE_TELEMETRY`, `_AUTO_MODE`, `_GATEWAY_MODEL_DISCOVERY`, `_EXPERIMENTAL_ADVISOR_TOOL`, `_SDK_FILE_CHECKPOINTING`, etc. — full list in the fetch log) — proving the grep methodology surfaces real flag names when they exist as plain strings, so its failure to find `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS` in the SAME binary is informative, not a broken probe.
  - **So the correct, narrower claim is: the function-hooks ENGINE and worker machinery predates 2.1.266 by at least 15 versions (2.1.251 already has it running code, not just placeholders — it has live error-handling paths for a crashed hooks worker) — but the literal env-var string `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS` was NOT found as plain text in 2.1.251's binary, unlike 23 sibling flags that were.** Two explanations are both live and UNVERIFIED beyond this: (a) the gate was added under a different name/mechanism in 2.1.251 and renamed to the current env var name in a later version (possibly exactly 2.1.266, which would make the blog's number right for the ENV VAR but wrong for the FEATURE), or (b) the check is constructed dynamically (string concatenation/computed property) and evades a plain `strings` scan even though it exists. **This is the report's clearest source-disagreement finding**: aitmpl.com's specific "2.1.266, verified through binary analysis" claim is **partially corroborated (the feature predates their claimed version) and partially unconfirmed/possibly wrong (the exact version number and what "exists" means — engine code vs. the specific enabling flag — are conflated in their claim)**. Neither claudefa.st nor the GitHub issue state a version number at all, so there was nothing to triangulate against for this specific figure beyond the binary itself.
- **One more corroborating primary-source detail found only in this binary-analysis pass, not in any of the three secondary sources**: the string table shows `"PreToolUse"`, `"tool.call"`, `"agent.spawn"`, `"prompt.section"`, `"tool.describe"`, and `"prompt.submit"` handled together in one function (`v$(e)`) that produces an error message for a specific misuse (calling something that "would wait on the turn this hook is holding" from inside these events). **This directly confirms, from compiled code rather than documentation, that classic event names like `"PreToolUse"` are themselves valid function-hook event identifiers inside the same switch/dispatch as the new dot-namespaced events (`tool.call`, `prompt.submit`, etc.)** — i.e. `classic.*` (seen in `sec-default`) is very likely a WILDCARD pattern over these literal classic names (`PreToolUse`, `PostToolUse`, etc.), not a separately-named bridge event. This refines, with primary evidence, the "classic.* is the seam to the existing hook system" finding recorded earlier in this report.
