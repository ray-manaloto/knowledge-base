## FINDINGS

Both findings below come from Batch 1 (`python/src/kb_setup/currency/sync.py`, `python/src/kb_setup/currency/run.py`). Batches 2 and 3 returned clean. I independently re-derived both findings by reading the cited functions in the working tree (== HEAD) and traced the call chains codex named; both hold up.

1. **[P2] View-provenance inference can misattribute a regenerated view to the wrong graph after a best-effort stamp-refresh failure.**
   `python/src/kb_setup/currency/sync.py:638-646` (`view_records`) infers "this view was just regenerated from the graph now on disk" purely from a byte-fingerprint diff against the *previously persisted* stamp (`unchanged = was is not None and str(was.get("identity","")) == identity`; when unchanged is False and a previous record exists, line 645 sets `graph_fp = primary_fp`, i.e. attributes the view to the CURRENT primary graph). That inference is sound only if the previously-persisted stamp is itself accurate. But `stamps.refresh_after_regen` (`python/src/kb_setup/stamps.py:64-78`) is explicitly best-effort: if writing the stamp raises `OSError`/`ValueError`/`TypeError`/`ImportError`, it prints a WARNING and swallows the exception, and its caller (`artifacts.generate`, `python/src/kb_setup/artifacts.py:124-125`) still returns 0 — i.e. a full `kb-artifacts` run that regenerated a view but whose stamp write failed is reported as a full success, leaving the *persisted* stamp stale relative to the *actual* (already-regenerated) view file on disk. If a later `kb-merge` then rewrites `graph.json` and calls its own best-effort restamp (`python/src/kb_setup/graphify_ops.py:143`, `regenerated_views` defaulting to `False`), `view_records` sees the view's identity has changed since the (stale) persisted record and — per the logic above — attributes the view to the *new, post-merge* primary graph, when it was actually generated against the *pre-merge* graph. `check_views` would then report that view as up to date when it is actually stale. This requires two independent conditions (a stamp-write failure during a `kb-artifacts` run, followed by an intervening `kb-merge`/`kb-label` before the stamp is repaired), so it is a narrow window, not a routine path — but it is a real false-clean, and it defeats exactly the signal `#182`/this diff was built to add.
   Codex's report additionally claimed the converse case — "a partial generator that emits byte-identical output retains old provenance and remains falsely stale" — also at `sync.py:638-645`. I could not independently confirm this half: `deep_artifact_fingerprint` (the `identity` value) is computed from directory entry-count + newest `mtime_ns` (`sync.py:560-571`), not content hashing, so any actual regeneration write should normally bump the identity regardless of whether the resulting bytes are unchanged — meaning the scenario as stated would require the generator to skip the write entirely (or the OS to not advance `mtime_ns`), which is unverified from the diff alone. Flagging this half as **unconfirmed** rather than dropping it.

2. **[P2] The "step 1 currently green" auto-apply gate does not see the new derived-views staleness signal, and `--json` output omits it entirely.**
   `python/src/kb_setup/currency/run.py:309-324`: `views.report(views.check_views(...))` is called only inside the `else:` (non-JSON) branch at line 324, after `payloads`/`lines` were already built without it. `_payload()` (`run.py:243-255`) has no `views` key, so `run --json` (and any consumer reading that JSON, including `apply`) has no visibility into view staleness at all.
   I traced the authorization path independently: `apply()` (`run.py:391-395`) builds its authorizing verdict via a **fresh** `_run_one(repo_root, spec)` call (`run.py:392`) → `decide(sync=status, upstream=up, moved=moved, observations=observations)` (`run.py:220`) — `decide()` (`python/src/kb_setup/currency/decide.py:358-445`) never receives or reads any views/`check_views` signal. Gate 6, "step 1 currently green" (`GATES[5]`, `decide.py:42`), is implemented by `_gate_sync` (`decide.py:317-355`), which only inspects `sync.drifted` and `sync.blind` — it does not call or consult `views.check_views` anywhere. So even though `check()` (step 1, `run.py:128`) now prints the views verdict as part of "step 1"'s output, the gate that actually decides "step 1 currently green" for auto-apply purposes is narrower than what step 1 now reports: a genuinely stale view (e.g. `graph.graphml` built from an old graph) does not block `_gate_sync`, and could not block an otherwise-6/6 auto-apply. This is a real, confirmed gap between the "six gates" contract described in `CLAUDE.md`/`decide.py`'s own docstring and what `#182`'s new signal actually participates in.
