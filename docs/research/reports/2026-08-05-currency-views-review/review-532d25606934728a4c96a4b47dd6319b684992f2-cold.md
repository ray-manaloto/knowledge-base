### P1 — Gate 6 does not block auto-apply when the derived-views check is UNVERIFIABLE
**`python/src/kb_setup/currency/run.py:230`** (feeding `python/src/kb_setup/currency/decide.py:355-380`)

`_run_one` computes `view_status = views.check_views(repo_root, spec)` (run.py:224) and
passes only `stale_views=view_status.stale` into `decide()` (run.py:225-230). Confirmed in
`views.py`: every `NOT_VERIFIABLE` return (missing/corrupt stamp at views.py:161-171,
unreadable primary at views.py:174, or the "blind" branch of `_verdict` at
views.py:200-203) leaves `ViewStatus.stale` as the empty default tuple `()`. `_gate_sync`
(decide.py:317-381) only raises an ambiguity when `stale_views` is truthy (decide.py:366);
it never inspects `view_status.state`, so a `NOT_VERIFIABLE` verdict is invisible to gate 6.
Consequence: if the other five gates pass, `decide()` sets `auto_apply=not ambiguities and
_has_upgrade(...)` = `True` (decide.py:471) even though the views check could not actually
verify anything.

This is the fail-open form of exactly the shape this same diff's own docstring says it exists
to close: decide.py:317-329's docstring states "What it must not do is stay silent, because
silence on this path is consent" — but that guarantee was implemented only for the STALE
case, not the sibling NOT_VERIFIABLE case, even though `views.py`'s own module doc says
NOT_VERIFIABLE must "Never [be] rendered as a pass" (views.py:89-90). Spot-check: `git diff`
shows `stale_views` is a wholly new parameter introduced by this diff (decide.py's diff
hunk adds the parameter, the `if stale_views:` branch, and the module docstring explaining
why gate 6 needed it) — so this is a gap in a change whose entire purpose was closing this
exact class of gap, not a pre-existing condition.

Not covered by any test in the diff: `tests/test_currency_views.py` only unit-tests
`views.py` in isolation (no reference to `_run_one`/`RunRecord`/`decide`), and the pre-existing
`tests/test_currency_decide.py` (unchanged by this diff) has zero references to `stale_views`
or `NOT_VERIFIABLE`. `tests/test_currency_run.py` stubs `_run_one` outright
(`monkeypatch.setattr(run, "_run_one", ...)`, line 126), so the integration path where this
bug actually lives is never exercised end-to-end by the suite.

Not the `hook_guard`/`checks_state` deliberate-shape pair named in the review brief — this is
a distinct mechanism (gate 6 of the currency-bump auto-apply decision), and its own module
doc commits to fail-closed ("silence is consent" — decide.py:329), so this is a genuine
inversion of that stated intent, not a documented trade-off.

### P2 — The computed view status is never attached to the run record; JSON output always reports `skip`
**`python/src/kb_setup/currency/run.py:232-239`**

`view_status` is computed at run.py:224 and used to build `stale_views` for `decide()`
(run.py:230), but the `report.RunRecord(...)` constructed immediately after (run.py:232-239)
omits the `views=` keyword entirely. `RunRecord.views` has
`default_factory=lambda: ViewStatus("", views_mod.SKIP)` (report.py:64-68), so every record
this diff produces silently falls back to `("", "skip")` regardless of what `check_views`
actually found. `_payload()` (run.py:254-273) then serializes `"views": asdict(record.views)`
(run.py:269) into the `--json` output — the exact machine-readable surface `_payload`'s own
docstring (run.py:259-262) says was added *because* "the human path prints the derived-views
verdict and the machine path did not... so a `--json` consumer... saw a record with no trace
of it (#182)." The fix for that gap is itself broken at the one call site that populates it.

Also uncovered by any test in the diff for the same reason as the P1 finding — `_run_one` is
never exercised end-to-end.

### P2 — Views can be certified against a graph a concurrent writer produced, not the one they were generated from (race, no locking anywhere in `kb_setup`)
**`python/src/kb_setup/currency/sync.py:667-675`**, corroborated at
**`python/src/kb_setup/artifacts.py:93-124`** (`stamps.snapshot_views` / `refresh_after_regen` bracket)

`view_records` (sync.py:595-681) takes an `observed_before` snapshot from the caller and, for
each declared view, certifies it against `primary_fp` — the **current on-disk** graph
fingerprint read at the moment `view_records` runs (sync.py:652), not the graph that was on
disk when the view's bytes actually changed — whenever the view's identity differs from the
snapshot (sync.py:667-675, `graph_fp = primary_fp`). `kb-artifacts` (`artifacts.py:93-124`),
`kb-label` (`graphify_ops.py`, confirmed via `views_before = stamps.snapshot_views(...)` at
its own bracket), and `kb-merge` (`graphify_ops.merge_chunk`) each independently snapshot,
run graphify subcommands sequentially, and certify — but nothing in `kb_setup` takes a lock
across these three operations (`grep -rn "FileLock\|flock\|fcntl\|filelock" python/src/kb_setup/`
returns nothing). If one of the other two rewrites `graphify-out/graph.json` after a given
view finishes being (re)generated inside another operation's bracket but before that
operation's `_certify_views` call reads the primary fingerprint, the view gets certified
against a graph it was never actually generated from, and `check_views` later reports `OK`.

This is the same failure shape the sync.py module docstring (sync.py:622-633) already
documents being fixed for the *intra*-process case ("cold review caught it... reproduced end
to end; `check_views` returned OK") — the fix (a before/after bracket) closes the unbounded-gap
version of the bug but does not close the *inter-process* version, because nothing prevents
two brackets from a different simultaneous invocation from interleaving. Given this repo's
documented single-agent, `kb-*`-task-serialized workflow (`mise-tasks-only.md`,
`do-not.md`), the practical likelihood is low, but nothing in the code enforces it — this is a
real, if narrow, gap rather than a documented trade-off.

### `.claude/settings.json:74` — "the codex plugin is not self-resolving on a clean profile"
Codex's literal claim: `"codex@openai-codex": true` (settings.json:74, new in this diff)
names a marketplace (`openai-codex`) that has no corresponding entry in the project's
`extraKnownMarketplaces` block (settings.json:76-117).

That premise is **true as stated** — there genuinely is no `openai-codex` entry in
`extraKnownMarketplaces` — but the framing that this is a defect specific to the new addition
does not hold up: **three plugins already committed before this diff** share the identical
property (`pr-review-toolkit@claude-plugins-official`, `skill-creator@claude-plugins-official`,
`claude-md-management@claude-plugins-official`, and `mise@brentmitchell25` — none of
`claude-plugins-official` or `brentmitchell25` appear in `extraKnownMarketplaces` either), and
`.claude/CLAUDE.md` documents this pattern explicitly ("Four more were enabled 2026-08-03
without needing a note here... all Ray's, all ordinary tooling"). Checked on this machine:
`~/.claude/plugins/known_marketplaces.json` already lists `claude-plugins-official`,
`brentmitchell25`, **and** `openai-codex` — i.e. resolution here depends on marketplaces
registered at the user/global level, not on the project's `extraKnownMarketplaces`. That IS a
real (pre-existing) gap for a genuinely clean profile with none of those globally registered —
but it is not new to this commit, and it is not unique to the codex addition; it is the
established (if under-documented at the invariant level — `do-not.md` #11 is specifically about
never *writing* to `~/.claude`, and is silent on *depending on* global registration for plugin
resolution) convention this repo already uses for "ordinary tooling" plugins. Downgraded from
codex's implicit P2 framing to an observation: worth a repo-wide note about the convention (all
five plugins, not just this one), not a defect introduced by this diff.
