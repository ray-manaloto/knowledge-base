## MISSING

**M1 — `events.warn` lands on stderr, not stdout. §1(a)'s central hedge is moot.** `_human_handlers` (`sinks.py:333-337`): the stdout handler gets `_MaxLevel(logging.WARNING)`, which admits only `levelno < WARNING` (`:299-301`); the stderr handler gets `setLevel(logging.WARNING)`. The docstring states it at `:323-324`. So the JSON on stdout cannot be polluted, there is **no ordering constraint to honour**, and the `capsys` assertion must read **`.err`**. Delete "emit BEFORE the JSON so the JSON remains the last stdout line" from the spec — an implementer coding to it will pin an ordering that isn't the mechanism.

**M2 — production wraps everything in an *offloaded* sink.** `cli.py:49` runs the whole dispatch inside `sinks.stdout_sink(jsonl_path=os.environ.get("KB_EVENTS_JSONL") or None)`, and `stdout_sink` defaults `offload=True` → `QueueHandler` + listener thread (`sinks.py:369-375`). So under `uv run kb-setup …` the warn is asynchronous relative to `print()`; a `2>&1`-combined capture is not ordered. Streams stay separate, so §5's "the stderr/log shows the four scrubbed names" is fine. A JSONL file sink exists but is env-gated (`cli.py:31,49`) and nothing under `.agent/` sets `KB_EVENTS_JSONL` — no file artifact by default.

**M3 — test with `capsys`, never `caplog`.** `_ensure_sink` (`events.py:184-216`) sets `logger.propagate = False` at `:216`, so records never reach root and `caplog` sees nothing. It uses `is_sink` rather than `if logger.handlers` specifically so pytest's capture handlers don't suppress emission (`:210-213`), and `_StdStreamHandler` resolves the stream at emit time (`sinks.py:197-222`) so `capsys` does see it. Unconfigured default handlers are not offloaded, so emission is synchronous under a plain `capsys` test.

**M4 — §5 line 38 is a probe that can only pass.** `env | grep -c '^AWS_'` in the operator's shell after the suite returns 4 whether or not the tests leak: a pytest child process cannot mutate its parent shell's environment. The leak is intra-session only. Drop that line or the spec ships a green light that measures nothing.

**M5 — §1(d)'s ordering-dependent sibling test is unsound under the ship gate.** `mise.toml:325` is `uv run pytest tests/ -x -q -n auto` (`-n auto` deliberately NOT in `addopts`, which is just `-q`). Under xdist's default `--dist load` tests are handed out per-test, so "a dedicated test at the end of the module" may land in a different worker than the leaking test, or run before it — non-deterministic, usually a pass-by-luck. It works only under §5's own `uv run pytest <files> -q`. `mise.toml:316` additionally records "nothing in `tests/` depended on execution order" as a property the suite has; this design would break it. **Order-independent alternative:** isolate inside each leaking test (`monkeypatch.setattr(os, "environ", dict(os.environ))`) and assert, in that same test, that a saved reference to the real `os._Environ` still holds the names.

**M6 — the `dict` isolation is safe here, with one boundary.** `dict` satisfies `MutableMapping[str, str]`, so `scrub_route_overrides`' annotation holds; `ty` sees nothing (runtime patch). None of the three wiring tests reaches a subprocess — preflight is stubbed in all of them — so the lost `putenv` semantics never bite. Boundary to write down: a test that spawns without an explicit `env=` would inherit the *original* C environ, so never use this isolation in a spawning test.
