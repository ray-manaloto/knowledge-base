Completed 2026-09-08. Offline pinned source/doc investigation plus one isolated probe of the exact pinned Rust scope module. No tracked files or user/global configuration were changed by this lane.

## 1. Import / automatic sync documentation and implementation

**Yes: Codex documents and implements categorized external-agent imports. The exact ChatGPT desktop Settings UI, persistent category preferences, and its automatic scheduling were not located in these pinned corpora.** The docs mirror says: "Use `externalAgentConfig/detect` to discover external-agent artifacts that can be migrated, then pass the selected entries to `externalAgentConfig/import`" (`sources/codex-docs/docs/learn.chatgpt.com/docs/app-server/index.md:1808`). The request example passes `migrationItems`, an `itemType`, `cwd`, and `source: "claude-code"` (`:1836-1845`). The per-category list is explicit at `:380`: config, skills, AGENTS.md, plugins, MCP server config, subagents, hooks, commands, sessions.

The primary enum is `ExternalAgentConfigMigrationItemType` (`sources/codex/codex-rs/app-server-protocol/src/protocol/v2/config.rs:732-762`): `CONFIG`, `SKILLS`, `AGENTS_MD`, `PLUGINS`, `MCP_SERVER_CONFIG`, `SUBAGENTS`, `HOOKS`, `COMMANDS`, `MEMORY`, `SESSIONS`. Each selected item carries a `cwd`; its comment states: "Null or empty means home-scoped migration; non-empty means repo-scoped migration" (`:846-851`). The service dispatches on the requested item type (`external-agent-migration/src/service.rs:192-220,328-394`). This establishes **per-request categories**, not how the desktop app persists or implements its checkboxes. `MigrationScope::from_cwd` walks to the nearest ancestor with a `.git` file/directory, with the supplied directory as fallback if none exists (`scope.rs:21-54`).

**UI negative-search control:** unrestricted-depth text search across both clones, including hidden/ignored files except `.git` internals, found neither `Import from another AI app` nor `Content to sync` (exit 1). The identical `rg -l -i --hidden --no-ignore -g '!**/.git/**'` command shape and roots with `shell_environment_policy` found 64 files (exit 0). Exact `automatic sync` found only enterprise plugin-marketplace syncing (`sources/codex-docs/docs/learn.chatgpt.com/docs/enterprise/plugin-management/index.md:183,185`). Broader import/sync spelling searches found real migration code; notably `app-server/tests/suite/v2/external_agent_import_sync.rs:119-157` explicitly calls detect/import RPCs to sync **sessions**. That is not evidence for a desktop automatic config-sync scheduler. Logs and search bounds are recorded below.

**The project target and the observed comment loss are present in Codex itself.** `sources/codex/codex-rs/external-agent-migration/src/service.rs:553-560` selects `$CODEX_HOME/config.toml` for home scope and `root.join(".codex").join("config.toml")` for repository scope. The independent MCP import selects the identical target at `:602-608`. Config import parses the whole existing file to `toml::Value`, merges missing settings, then rewrites it (`:582-595`); MCP import does the same when it adds at least one missing server (`:626-636`). The shared writer is `toml::to_string_pretty(value)` followed by `fs::write(...)` (`external-agent-migration/src/config_values.rs:77-80`). Inference from this code: semantic TOML keys survive, while comments and original formatting do not.

The env conversion is exact: `settings.get("env")` becomes `inherit = "core"` and `set = ...` inside `shell_environment_policy` (`external-agent-migration/src/source/mod.rs:44-57`). The Claude adapter names `.claude/settings.json` (`source/cla.rs:20-22`) and overlays `settings.local.json` (`:76-92`). MCP import names `.mcp.json`, reads its JSON, and produces the `mcp_servers` table (`external-agent-migration/src/mcp.rs:10,69-91`); it can also read project entries from `.claude.json` (`:92-113`). These paths are relative to `sources/codex/codex-rs/`.

**Disabling Settings alone need not protect this file.** MCP server import is a separate branch and writer (`service.rs:328-344`, `:602-637`). Important bound: this implementation does not rewrite config unconditionally on every import; Settings needs a missing value (`:590-595`), and MCP needs a new server name (`:633-635`). Repeated writes with no semantic additions, or env re-addition while only MCP is requested, require another explanation or a different application implementation/version. These sources establish a compatible mechanism, not which process actually caused the user's observed writes.

The preservation rules are also explicit: `config_values.rs:8-37` recursively inserts missing settings without replacing existing values; `:40-74` inserts only absent MCP **server names**, preserving existing same-named server tables. Thus repeatedly restoring a tracked version that omits an imported server can repeatedly create a fresh addition and trigger comment loss. That is a conditional explanation, not a claim that this restoration cycle occurred. The existing source test `service_tests/general/config_import.rs:5-64` verifies that reimport of an existing same-named server leaves file bytes unchanged; inspected, not executed in this lane.

## 2. Codex config writers and external configuration APIs

**Yes.** The external-agent migration service above writes project `.codex/config.toml` directly. The app-server protocol exposes `ExternalAgentConfigImport => "externalAgentConfig/import"` (`sources/codex/codex-rs/app-server-protocol/src/protocol/common.rs:1334-1337`). `app-server/src/message_processor.rs:998-1001` routes the request into the migration processor, whose `import_external_agent_config` passes requested items into `migration_service.import(...)` (`app-server/src/external_agent_migration/processor.rs:515-528`). That reaches the direct project-file writers cited in answer 1. An external client can therefore cause this write through Codex's app-server API; direct editing by the desktop application is not the only possible mechanism.

**Separate API, different write boundary:** `config/value/write` and `config/batchWrite` accept JSON key/value edits, merge strategies, optional `filePath`, and optional `expectedVersion` (`app-server-protocol/src/protocol/v2/config.rs:1059-1084`). Despite the generic-looking `filePath`, `ConfigManagerService::apply_edits` permits only its user-config path: `ConfigWriteErrorCode::ConfigLayerReadonly`, "Only writes to the user config are allowed" (`app-server/src/config_manager_service.rs:216-235`). The two entry points delegate to that check (`:193-213`), then use `ConfigEditsBuilder::for_config_path(...).apply()` (`:437-442`). This readonly error is an API restriction, not protection applied to the filesystem or to the migration service. Do not infer that an arbitrary project target is accepted by this generic API.

The migration request is item selection, not an arbitrary config-content push: `ExternalAgentConfigImportParams` carries `migration_items`, initiating-product `source`, analytics `provider_id`, and `migration_source` (`app-server-protocol/src/protocol/v2/config.rs:891-904`). The importer reads the external files itself. No desktop RPC trace or running-app binary was inspected; the actual culprit process/API remains unproven.

There is also an internal general-purpose persistence engine: `ConfigEditsBuilder::for_config_path(config_path)` accepts an explicit path (`core/src/config/edit.rs:786-811`), reads it into `toml_edit::DocumentMut`, applies edits, and writes atomically (`:741-781`). It intentionally follows symlink write paths (`:749`). Its formatting-aware representation differs from the importer's `toml::Value` serialization; do not attribute the importer's comment-loss behavior to every Codex writer. The public config RPC's user-layer restriction is imposed by its caller, not by this builder.

## 3. Project configuration protection and relocation

**No documented project-file lock/immutable/generated marker, generic include, or arbitrary project-config filename override was found in the searched configuration docs and definitions. The source does provide a useful importer-specific symlink guard.** This is bounded research, not a claim about unavailable desktop source or future versions. Controls: exact candidate knob spellings returned exit 1; the same command shape/root set for the known `project_root_markers` returned 45 lines, exit 0. The broader protection search produced 81 files and led to the real mechanisms below; search spelling alone did not decide this answer.

- **Fixed project lookup:** the loader walks ancestors from `cwd` to the detected project root (`sources/codex/codex-rs/config/src/loader/mod.rs:1707-1720`), constructs `dir.join(".codex")` and `.join(CONFIG_TOML_FILE)`, and reads/parses that file (`:1725-1752`). `CONFIG_TOML_FILE = "config.toml"` is defined in `config/src/lib.rs:40`. Missing config still creates a project-layer entry so other assets can load (`loader/mod.rs:1802-1811`).
- **Environment:** `CODEX_HOME` selects the user/state directory (`utils/home-dir/src/lib.rs:13-46`; docs `config-file/config-advanced/index.md:80-89`). It does not change the repository import target: `root/.codex/config.toml` is selected independently of `codex_home` in `external-agent-migration/src/service.rs:558-560` and `:606-608`.
- **Overrides:** `-c/--config` is repeated `key=value`, not a file include (`utils/cli/src/config_override.rs:19-36`, `:49-62`). CLI/session values outrank project values, but do not stop physical rewrites (docs `config-file/config-basic/index.md:32-39`; loader `config/src/loader/README.md:24-35`). Profiles are user-layer files under `$CODEX_HOME`, lower precedence than project config, not a project replacement.
- **`cwd` / search boundary:** `--cd/-C` is an actual CLI working-directory argument (`utils/cli/src/shared_options.rs:67-68`). `project_root_markers` changes discovery boundaries; `[]` treats cwd as the root (docs `config-file/config-advanced/index.md:158-169`). Those select which fixed `.codex/config.toml` paths are read. They do not redirect the migration destination, whose scope uses its own `.git` traversal (`external-agent-migration/src/scope.rs:43-54`). Changing Codex's launch cwd cannot prevent an external client from sending this repository as an import item's cwd.
- **Project trust:** disabled project layers are filtered from effective readers (`config/src/state.rs:478-484`); docs explicitly say untrusted project config/hooks/rules are skipped (`config-file/config-basic/index.md:43`). This loses intended project behavior and does not protect the file from import writes. `MigrationScope::from_cwd` resolves a repository filesystem scope, not a trust check (`external-agent-migration/src/scope.rs:21-71`).
- **Internal loader control:** `LoaderOverrides.ignore_project_config` exists (`config/src/state.rs:54-56`), and `loader/mod.rs:364` tests it. `ConfigManager::load_non_project_config` uses it to avoid discovering a project from the app-server process cwd (`app-server/src/config_manager.rs:147-152`). This is a Rust loader option, not a discovered project TOML setting; it controls consumption rather than the independent import writer.
- **Sandbox protection:** Codex documents protected `.codex` paths for command execution (docs `config-file/config-basic/index.md:75-83`). It does not turn a repo file into OS-wide read-only data. The importer uses direct `std::fs::write` (`external-agent-migration/src/config_values.rs:80`) without an agent shell/tool approval path.
- **Concrete importer guard:** `MigrationScope::repository` returns `None` if any of `.codex`, `.codex/config.toml`, `.codex/agents`, `.codex/hooks`, `.agents`, or `.agents/skills` is redirected (`external-agent-migration/src/scope.rs:57-71`). `is_redirected_destination` checks `symlink_metadata(...).file_type().is_symlink()` (plus Windows reparse points, `:90-101`). Each config/MCP/hooks/agents/skills importer first resolves that scope, so a repository-local symlink at `.codex/config.toml` opts that scope out of those branches in this importer. **Tested directly against the pinned module:** regular-file control accepted; relative-symlink arm skipped; restored regular-file control accepted. See the retained probe/log below. The guard tests link type, not whether the target escapes the repo. It does not automatically block the separate plugins/session machinery or every other writer.
- **Reader compatibility of a symlink:** project config is read with default `ReadFileOptions` and no sandbox context (`config/src/loader/mod.rs:1744-1752`); the default is `follow_symlinks: true` (`file-system/src/lib.rs:48-57`), and local reads follow links under that option (`exec-server/src/local_file_system.rs:581-604`). This is source evidence for compatibility. The probe checked an ordinary filesystem read, not the full Codex loader or the desktop app.

## Mitigations within repository control

1. **Candidate for a separate reviewed change: keep owned config in a repository-local regular TOML file and make `.codex/config.toml` a relative symlink to it.** For example, `.codex/config.toml -> owned-config.toml`, both tracked and entirely inside this repo. The scope guard and control probe support protection against the pinned migration path, while reader defaults support continued config loading. It preserves the `.codex` folder for agent/hook discovery and requires no user/global writes. This report does not implement the change. Before adopting it, verify full Codex loading and the actual desktop sync behavior on an isolated fixture; an application that follows/replaces symlinks directly, or another config writer, can bypass this particular protection.
2. **Keep explanatory material in an adjacent tracked document if the import target must remain generated.** A documented generated-file workflow can retain the rationale outside the serialization target; the importer has no proven generated-file marker to honor. This preserves comments as documentation but does not itself prevent settings drift. Regenerating the tracked snapshot after every import can re-create missing-server additions and repeat the write cycle described in answer 1.
3. **Detect changes across the full tracked inventory.** A repo check can compare `.codex/config.toml`, `.codex/hooks.json`, and the seven agent files against the intended committed/config-generated bytes. This is detection, not prevention; preserve diffs as evidence and avoid blind restoration loops. No check was added in this research lane.

Unchecking MCP servers as well as Settings, or disabling Automatic sync, is an owner-controlled application experiment suggested by the source category split; it is outside repository control and its desktop semantics are not established by these sources. `CODEX_HOME`, a profile, sandbox settings, and project trust are not equivalent replacements for stopping the external writer. No user/global config, filesystem permissions, application preferences, or tracked config was altered here.
