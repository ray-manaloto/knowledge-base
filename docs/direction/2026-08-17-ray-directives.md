### Telemetry — PROBED 2026-08-17. It is the right instrument, for a different question

Ray: *"telemetry would help identify what exactly is available from the messaging back
and forth."* **Correct, and it is worth setting up — but it answers the MESSAGING
question, not the CAPABILITY one.** Both halves matter; conflating them would send the
next session looking for a ceiling that telemetry never carries.

Source: `https://code.claude.com/docs/en/monitoring-usage.md` → HTTP 200, 136,332 bytes
(bogus path → 404, so the probe discriminates).

**What telemetry gives — and it is a lot:**

- `CLAUDE_CODE_ENABLE_TELEMETRY=1` plus the standard `OTEL_*` exporter vars.
- **`OTEL_LOG_RAW_API_BODIES`** emits `claude_code.api_request_body` and
  `claude_code.api_response_body`. In `file:<dir>` mode these are written
  **untruncated** to `<dir>/<uuid>.request.json` and `<dir>/<request_id>.response.json`,
  with a `body_ref` pointer in the event. Inline mode (`=1`) truncates at 60 KB.
  → This is literally the full Messages API request and response JSON. It settles
  *empirically* what Claude Code sends, including the `max_tokens` it requests per call,
  and what came back.
- A rich event taxonomy well suited to the session-review workflow — far more structured
  than parsing transcripts: `api_request`, `api_error`, `api_refusal`,
  `api_retries_exhausted`, `tool_decision`, `tool_result`, `hook_execution_start/complete`,
  `compaction`, `cost.usage`, `active_time.total`, `commit.count`.
- `stop_reason` is an emitted attribute, so a call that **hit** the cap is directly
  observable (`max_tokens` is one of its values).

**What telemetry does NOT give — measured, not assumed:**

Across the whole 136 KB page, `max_tokens` appears **exactly once**, and only as a
*value of the `stop_reason` attribute*; `context window` appears once, in an unrelated
`/compact` note. There is no metric or attribute carrying a model's **capability
limits**, because the Messages API response body has no capabilities field — the
response carries `id`, `content`, `usage`, `stop_reason`, not `max_tokens` ceilings.

**So the correct division of labour:**

| question | instrument |
|---|---|
| What does Claude Code *send/receive*? What did this session actually do? | **Telemetry** (`OTEL_LOG_RAW_API_BODIES=file:<dir>`) |
| What is the model's *ceiling*? | **Models API** `/v1/models/{id}` → `max_tokens`; docs `.md` as the credential-free fallback |

**On Ray's staleness objection to docs `.md`:** the objection is right in direction and
the fix is not telemetry. Docs are fetched live so they are current-as-of-fetch, but they
lag the API by whatever the docs pipeline lags — and nothing detects that lag. The
Models API is the only source that cannot be stale, because it *is* the runtime.
Telemetry does not close this gap; `claude setup-token` might.

**Consent / blast radius, flagged because it is a real decision.** Raw bodies contain the
**entire conversation history**, and the docs state that enabling `OTEL_LOG_RAW_API_BODIES`
"implies consent to everything `OTEL_LOG_USER_PROMPTS`, `OTEL_LOG_TOOL_DETAILS`, and
`OTEL_LOG_TOOL_CONTENT` would reveal". In `file:<dir>` mode that lands on disk
unencrypted and uncapped. Choose the directory deliberately (gitignored, outside the
repo or under `.agent/`), and decide retention before enabling — not after.

### The correction that reframes the original question

`max_tokens` is **per-MODEL, not per-effort**. The `capabilities` tree exposes effort
levels as *booleans* (`capabilities["effort"]["max"]["supported"]`), not per-effort token
ceilings — effort governs how many tokens the model *spends*, not the ceiling it may
spend up to. A resolver taking an `effort` argument would have a parameter it could only
ever ignore. Verified against the bundled `claude-api` reference, not recalled.

## Standing mandates this directive adds or sharpens

1. **Skill → mise task → python module/function**, each layer optionally taking
   hints/arguments. Sharpens the existing `mise-tasks-only` / `zero-bash-logic` rules by
   adding the *skill* layer and the *optional-argument* requirement.
2. **All project code lives in the python library** — nothing implemented only in a
   skill, a task body, or a workflow script.
3. **Generate, don't hand-write** — `datamodel-code-generator` and peers; enums for
   error codes and return values; a lint skip is acceptable only after research plus an
   upstream issue, with zero skips as the goal.
4. **Search for existing tools before writing any code**, preferring structured output
   from tools already depended on (mise/hk/uv/claude-code).
5. **All output to a log file** via the python logging library.
6. **Visual-first plans/specs/implementations** — `/wait-what` output style, mermaid,
   components + dependencies, generated from source and kept in sync with zero/minimal
   agent work.
7. **Skills are created with `/skill-creator`**, assisted by `/writing-for-agents`.
8. **A state machine library** eventually replaces complex conditional logic and yields
   visual workflows.
9. **No reliance on tools from `~/.config/mise/mise.toml`** — everything this repo needs
   is pinned in the project's own `mise.toml` / `pyproject.toml`.
10. **Context budget per task: ideally under 200K tokens**, achieved by decomposition.
