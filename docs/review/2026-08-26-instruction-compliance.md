## 3. Vague or ambiguous — what a cold agent could get wrong

1. **`do-not.md` #2 mixes a machine-checkable ban list with inline historical narrative, and this exact round re-made a misreading the file already warns about.** The rule's operative text bans exactly three things — `graphify hook install`, `graphify extract --global`, `graphify global add` — but the same numbered entry also carries a paragraph of corrective history about `watch` ("`watch` was in this list and never belonged to it (narrowed 2026-08-01)... A ban filed under a reason that does not apply is one nobody can reason about later"). A cold reader skimming the entry's *shape* (a bulleted "do not" list followed by prose) rather than its precise operative sentence will count `watch`, `global list`, `global path`, and `global remove` as banned too — which is exactly what happened in `what-reaches-what.html` this round, filed as issue `#522`'s original body, and only caught because Ray personally re-asked "what are the 6". The rule itself already documents one prior instance of this same misreading (the `watch` narrowing), and a second cold agent — codex or antigravity, with no memory of this session's correction — has no signal in the file's current form that would prevent a third. **Prescription:** hoist the operative ban list into one unambiguous, machine-diffable line (e.g. a fenced block or a literal Python set literal referenced by a test) separate from the surrounding narrative, so "what is banned" is answerable without reading prose.
2. **The `kb_setup.graph_first` PreToolUse hook's "MANDATORY" wording surfaced during this very review, in direct tension with the orchestrating agent's explicit read-only scope.** This review's own dispatch said: *"READ ONLY on the repo's source. You may run `git`, `gh issue view`, and read files... Do NOT run `mise run` anything that writes, do NOT run graphify write verbs."* Multiple times during this session, a tool-level system reminder fired: *"MANDATORY: graphify-out/graph.json exists. You MUST run `graphify query "<question>"` before grepping raw files."* Nothing in this repo's rules states which instruction wins when a hook's imperative language ("MANDATORY", "MUST") conflicts with an orchestrating agent's explicit narrower scope for a specific task. In this session the hook turned out to be advisory-only for `grep`-via-Bash (no call was actually blocked), but a cold agent — especially one on a different harness that treats such reminders as hard constraints, or one without this session's context that the calling agent's scope overrides it — could stall trying to satisfy a `graphify query` call that its task explicitly forbade running, or could wrongly conclude the read-only constraint had been silently lifted. `mise-tasks-only.md` documents the hook as a *deny* mechanism elsewhere but does not document its advisory-only behavior for review/audit-scoped sessions.
3. **"have graphify deeply extract and reflect on these [two Pyrefly blog URLs]" (item 4) is ambiguous between two different repo mechanisms.** This repo has two distinct "deep extraction" pipelines: the standard prose-ingestion path for docs/URLs (`kb-add` → host-agent extraction → `kb-merge`, per the `kb-curator` skill), and the newly-unparked `kb-graphify-native-extract` task, which drives graphify's own CLI-based deep extraction over a **cloned git repository** (`sources/<name>/`), not an arbitrary web page. The directive's phrase "graphify deeply extract" does not disambiguate, and this round's dominant activity was restoring and reasoning about the *native-extract* path (four of nine commits touch it directly or in artifacts). A cold agent picking up issue `#528` section A, primed by this round's own emphasis, could plausibly try to point `kb-graphify-native-extract` at two blog URLs — a use case it was never built for — instead of the correct `kb-add`/host-agent path.
4. **Item 5's "automate daily as morning brief" names no mechanism, and this repo's constraints rule out the obvious one.** The directive: *"this needs to be something we automate daily as morning brief that an agent team can create/review/synthesize."* This repo has no CI (`gh-cli-watch.md`: *".github/ does not exist here"*) and forbids `.sh` scripts and inline shell logic outright (`zero-bash-logic.md`), which rules out a naive cron-triggered shell script — the most obvious literal reading of "automate daily." The session's own tool surface includes `CronCreate`/`CronList` and a `schedule` skill plus a `loop` skill, none of which are mentioned in issue `#528` section B or anywhere else this round. A cold agent without visibility into this session's available tooling could reach for a bash cron entry by default, directly violating `zero-bash-logic.md`, or could wrongly conclude no mechanism exists in this environment at all.
5. **Item 9 — "are there AST tree-sitter/LSP tools/or other tools we can use to help analyze our config files better?" — reads two different ways, and the round answered mostly one of them.** One reading: tools that analyze the *Python code* that reads config files (call/data-flow analysis) — this is what `what-the-ast-cannot-see.html` and the `code_intel` `config_edges` lane actually deliver. The other reading: tools that analyze the *config files themselves* (TOML/PKL/YAML syntax, schema, structure) — e.g. `taplo` (already pinned here for TOML), a PKL LSP, `yamllint`. Issue `#528` section D partially notices the gap ("this asks wider — TOML/PKL/YAML have their own tooling") but does not resolve it, and none of the five published artifacts addresses config-file-native tooling at all. A cold agent handed this item cold, without the context that the round already leaned toward the narrower "code that reads config" reading, could reasonably answer only the other half and consider the item done.
6. **Item 3's second clause — "we might need to revisit some of the pre-existing rules/requirements as they might have been misunderstood... to not cause issues going forward" — has no stated scope or stopping condition.** "Some" names no specific files, no count, and no criterion for what counts as needing revision versus being fine as written. Issue `#527` bounds this round's response to two files (`do-not.md`, `ai-cli-invocation.md`) and one owed action ("re-read every rule in `.claude/rules/` against what the repo actually does"), but a cold agent resuming `#527` has no way to tell from the directive itself whether reading those two files satisfies "some of the pre-existing rules" or whether the instruction is a standing mandate to keep auditing all ~48 instruction files indefinitely. Left as written, this item can be closed after one file or never closed at all, and both readings are defensible.
7. **Item 1's "provide suggestions of checks we are making that can definitely provide the health status of the project currently" is ambiguous between auditing existing checks and proposing new ones.** "Checks we are making" most naturally reads as checks *already in use* (an inventory/audit ask), but issue `#525` interprets it exclusively as a request for **new** checks to add ("Suggested additional checks" — nine proposals, none of which restate the four Ray named). A cold agent could instead spend its effort enumerating the current gate set (`kb-gates`, `lint`, `test`, `brain-audit`, `eval`) and conclude that satisfies the ask, producing a materially different — and less useful — deliverable than the one this round chose.
