The Corpus Cannot Answer

We asked the knowledge base one real architecture question, the way Ray specified. Then we counted the backlog that is supposed to be fixing it. Both answers were worse than expected, and they are the same answer.

Could an agent get a sourced answer from this corpus alone? No.

Seven probes, control-armed. The graph contributed exactly one substantive fact — the 512 MiB cap, which is also the single most-documented line in graphify's own README. Every load-bearing citation in the answer came from grep and sed on files, not from the graph.

Why it failed — and it is not staleness

The lane named seven distinct causes. The structural one subsumes the rest:

The corpus indexes the corpus's dependencies, not the corpus's decisions. mise.toml, .claude/rules/**, python/src/kb_setup/**, docs/direction/** and the GitHub issues are not ingested. The strings #130, #120, federate and shard appear in neither graph layer. Every fact that decided the answer lives in the un-ingested half.

The other six, briefly

  1. The default query mode is the wrong arm and never says so. --prose --idf is the only usable one.
  2. --idf only works if you already know the corpus's wording. The control scored 37.14 using the node's own title; the same idea phrased as a question scored nothing. A spelling bound — you must know the answer to retrieve it.
  3. Truncation is the default outcome and the tool explicitly warns the prefix is not evidence of absence — under rc=0, which an agent will read as success.
  4. Every query prints a node-ID collision warning: the graph uses the pre-#1504 scheme, so same-stem files across 85 sources collide by construction.
  5. The graph cannot be rebuilt anyway. graphify-out/.build-failure.json, stamped 2026-08-27: extract failed closed. It is 6 days stale and #397 blocks the refresh.
  6. The reflection layer was the one thing that worked. LESSONS.md:1417 records that a prior agent fabricated a Ray ruling on this exact topic and that it propagated through handoffs.

A premise I gave you was wrong, and the lane caught it

I told you #120 (the duplicated repo:: prefix) was open and that federating was the durable fix. #120 already shipped. graph.py:2552 is headed “THE FIX FOR #120”, it recovered 184 MB — 33% of the file, and graph_checks.py:52 gates it on every build (_MAX_SEPARATORS = 1). It landed 2026-08-05; today's graph was built 2026-08-21, so its bytes are real data.

I did not invent that — I read it off mise.toml:911, which still says “Both open.” The comment is stale by three weeks, and it is the exact shape of failure this repo keeps filing issues about: a correctly-cited fact that stopped being true.

What it changes: #120 offers no remaining headroom — that lever is already spent. Federation (#130) is the only one left, and the corpus argues it loses nothing, because the aggregate holds 85 sources with zero cross-source edges. It is a concatenation, not a join.

What this implies for the round you chose

You picked the substrate — headline word Reachable. The measurement supports that and sharpens it in one way you should know before I draft the goal:

“Our code isn't in the graph” was too narrow a diagnosis. Our doctrine isn't in it either — mise.toml, the rules, the issues, the directives. A corpus that indexes only its dependencies can never answer a question about its own decisions, and that is the class of question every round actually asks.
