The graph knew.
I never asked it.

Ray asked why I didn't know graphify prs existed. The honest answer is not that the corpus lacked it. One query would have found it — and I ran that query only after being told the feature was there.

The query I should have run first

This is the actual output, run after Ray pointed at the README. Third result:

$ mise run kb-query -- "graphify prs PR dashboard review queue worktree mapping"

NODE Dashboard   [src=ecc2/src/tui/dashboard.rs loc=L82]
NODE Worktree    [src= community=zed/src/lib.rs]
NODE graphify prs — graph-aware PR dashboard. Fast terminal overview
     of open PRs…  [src=graphify/prs.py loc=L1 community=prs.py]
NODE graphify    [src=graphify/README.md]

The graph holds graphify/prs.py, the README that documents it, and the feature's own one-line description. It was never a corpus gap.

Three places could have told me. I consulted the two that lie.

Both stale sources are stale by the same 14 command paths

Corrected after publication. This section first said 18 and named callflow-html as an example. A cold lane re-derived the diff against upstream and refuted both: my list held 17 items, of which callflow-html and status are in --help after all (export callflow-html at help line 122; hook status listed under its parent), while export neo4j and the whole provider parent command were missed. The corrected figure is 14 undocumented command paths. The original claim is left visible rather than quietly swapped, because it had already been acted on.

graphify --help does not list everything graphify can do. Re-derived against installed 0.9.50 and confirmed not fork-introduced:

prs ← · provider (a whole parent command, 4 subcommands) · cache-check · merge-chunks · merge-semantic · hook-check · hook-guard · and 7 of export's 8 formats

The severity is narrower than it first looked, and that matters. Every one of these except prs, hook-check and hook-guard prints its own usage when run with bad or missing arguments — so the defect is specifically that the top-level listing never tells you the verb exists to try. prs is the standout: fully working, eight usage lines in the README, and zero discoverability from the CLI.

Root cause, read from the source: __main__.py's help output is roughly 140 hand-written print() calls, not generated from dispatch_command()'s own table. Two independently maintained lists that drifted.

What I did wrong, precisely

I treated a tool's --help as the inventory of that tool's features. This repo has a rule about exactly this shape — probes-need-a-control-arm.md: “Source beats issue tracker. A tool's claim about a platform ages.” I applied it to issue trackers and vendored docs and never to the CLI in front of me.

Worse: I ran a --help grep for pr|impact|affect|risk|diff|blast, got affected back, and stopped. A hit made the probe feel answered. A 0-result grep needs a control arm; so does a 1-result one that confirms what you expected.

The structural half — and it is the more useful half

Two mechanisms let that mistake pass unchallenged, and neither is about my judgement.

MechanismWhat it doesWhy it didn't help
graph_first DENIES a broad source search until one graph query has run this session Satisfied once. After my first query about the code I was changing, it fell silent for the rest of the session. It enforces ask the graph once, not ask the graph about this.
/graphify SKILL.md Injects a Usage block into every session as authoritative-looking reference Generated and unchecked. Nothing compares it to the installed CLI, so a feature can ship and the skill will keep describing the version before it — in context, at the top, on every turn.

The skill one is the sharper problem. A stale doc on disk is inert until someone opens it; a stale doc auto-loaded into every session actively displaces the live source, because it arrives first and looks canonical.

Three fixes, cheapest first

habit — costs nothing

Query the graph about the TOOL, not just the code

Before driving any pinned tool in a new way, one kb-query against its own source and README. It would have cost one command here and saved this entire exchange.

gate — small, mechanical

Assert the skill's command list against the installed CLI

The dispatch table is grep-able (cmd == "…") and the skill's Usage block is a fixed list. A check that fails when the installed CLI has a verb the skill never mentions would have caught all 18 — and would catch the next one, on the next bump.

judgement — yours

Decide whether graph_first should be per-topic

A session-scoped satisfaction is cheap and un-annoying; a per-topic one would have forced the query that mattered. It is a real trade — more denials, more friction — and worth deciding deliberately rather than inheriting.

A correction, stated because I nearly shipped it

Mid-investigation I grepped sources/graphify/README.md against the graph, got 0, and was one step from reporting “graphify's README is not ingested.” It is. The graph stores it relativized, as graphify/README.md — 6 nodes — and my probe carried a path prefix the graph never uses.

That is the repo's own a path prefix is an identity claim lesson, recorded two rounds ago, walked into again. What saved it was a control arm that happened to print neighbouring paths.

The separate finding in #551 survives that correction, and was re-probed without any prefix assumption: no node in the graph has a source_file ending in graphify_sdk.py, while hook_guard.py returns 40+. That absence is real. This one was my probe.
