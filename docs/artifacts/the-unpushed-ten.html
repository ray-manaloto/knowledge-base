The Unpushed Ten

A merge gate that checks the right commit, and never asks whether it is the commit you meant. Ten reviewed commits stayed behind — and the same command that left them behind deleted the branch holding them.

How it happened

  1. Shipping and pushing are the same action here. kb-ship pushes the branch and opens or updates the PR — and it refuses to do either without a kb-review receipt for HEAD.
  2. The last successful ship was at 317c79ed, at 00:07. That commit touches only graphify-out/memory/, so it shipped on the ancestor-receipt exemption against the receipt for 4c156648.
  3. Then the round committed ten more times with no receipt. The gates kept running — artifacts exist at 01:39 and 03:58 — so the work was being validated the whole time. It simply could not leave the machine.
  4. The handoff predicted exactly this. It said: "NO review receipt for HEAD … kb-ship and kb-land will both refuse."
  5. The land half of that prediction is wrong, and that is the defect. kb-land validates the PR head, not local HEAD — on purpose, so that a commit pushed by some other route cannot merge unreviewed. The PR head was 317c79ed, which had coverage. So it merged.
  6. Nothing compares the two heads. The author reasoned about local being behind the PR head. Local being ahead of it was never a case anyone wrote down.

The question nobody asked

Why this isn't just operator error

Every surviving artifact reads green. land printed OK — PR #482 merged, main synced. The receipt it cited was genuine. The gates were genuine. Nothing in the output says the one sentence that would have stopped it: your local branch is ten commits ahead of what I am about to merge.

It is also self-concealing: the same command that merges the wrong state deletes the branch holding the right one.

The commits survived only because the SHA was still resolvable and the branch was recreated within minutes. Left alone, they were reflog archaeology.

What would fix it

Before merging, resolve the local branch the PR head belongs to and refuse when local is strictly ahead — naming the count and the commits, in the shape of every other refusal in that module, and failing closed when the local branch cannot be resolved. This weakens nothing: the PR-head check stays exactly as it is, and the missing question gets asked beside it.

Worth pairing with it: refuse --delete-branch while unmerged local commits exist on that branch, so a mistake stays recoverable.

A second, smaller finding

A comment in the same module states that land "deletes the remote branch and leaves the local one." Measured: both were deleted — control-armed with git ls-remote, which returned a line for main and nothing for the branch, so the probe discriminates.

That sentence is the stated justification for how the ship path handles an already-merged PR. So it is a comment defending a real behaviour while describing its mechanism backwards — the shape that quietly disarms the next reviewer, because nobody re-reads a comment they agree with.
