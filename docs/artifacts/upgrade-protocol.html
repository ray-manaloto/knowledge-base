The Upgrade Protocol

Upgrading a dependency is not an edit. It is a pipeline of about a dozen stages, and today an agent hand-carries every one of them. This is what I understand you want built — and the four places I could be wrong.

What a single upgrade actually has to do

Every stage below was exercised by hand in this session, on five tools. That is the evidence this table rests on — not a design sketch.

The gap is mostly sequencing: nothing chains the stages, so an agent is the sequencer, and an agent forgets stage 3. But it is not only sequencing. The shape you asked for

Three layers, each a thin seam over the one below. The flags are the only place agent work enters.

# layer 1 — the skill, the only thing an agent calls
/upgrade <dependency> --deep-extract --reflect --artifacts

       │  a seam. no logic.
       ▼
# layer 2 — the mise task
mise run upgrade -- <dependency> --deep-extract ...

       │  a seam. one command. zero bash logic.
       ▼
# layer 3 — the python module, where all logic lives
kb_setup.upgrade.run(dependency, deep_extract=, reflect=, artifacts=)

# and the wrapper, same three layers
/upgrade-all              → every dependency that stage 1 reports behind
/upgrade a,b,c            → an explicit list

Why every previous attempt failed

Your read is that small changes keep not working. The evidence from today says something sharper than “too small”.

Each stage has its own checker, and each checker reads a different file. mise ls --current reads mise.toml. The currency engine reaches versions through mise_key, also mise.toml. Nothing reads mise.lock — so today a bump moved the pin, the manifests and the binary, and all seven gates went green over a lockfile still holding the old checksums.

That is not a missing feature. It is the absence of one object that knows a dependency has a set of artifacts and that all of them must agree. Every fix so far has added another checker to the pile instead of adding that object — which is exactly the pattern you are describing as broken.

The design consequence

If there is one thing to carry from the current system into a rewrite, it is not the code. It is currency.toml's ~2,100 lines of per-tool judgment — tag prefixes, version patterns, platform gates, and comments recording why. A generated mapping would recreate the config and lose the judgment, and a wrong tag scheme produces permanent false drift, which trains readers to ignore the report.

Four things I could be wrong about

These are the grilling questions. I am not dispatching a plan until they are settled, because each one changes what gets built.

1 · Where the state lives

A pipeline that can stop at stage 9 and resume needs to know where it stopped. Three answers, and they are not close to equivalent: derive it from the filesystem every time (no state to corrupt, but every query re-reads everything); a per-dependency record in the repo (resumable, reviewable, and it becomes the typed status enum — but it can lie); or a real workflow engine with a database (durable, retryable, and a new operational dependency for a repo that currently has none).

2 · Whether “latest” is ever an agent decision

Today an advisor deliberately deferred two minor linter bumps because they gate ~100 markdown files, and said to read the release notes first. If upgrading is zero-agent, that judgment has nowhere to go — so either the pipeline gains a “risky, needs review” verdict, or it upgrades blindly and the gates catch it after the fact.

3 · What atomicity means

One dependency, one commit, one PR? Or one batch? It decides whether a failing stage rolls back, and whether a 30-dependency sweep produces one PR or thirty.

4 · What the code generator can actually own

You want generation over hand-writing. mise and uv do publish JSON Schemas — but they describe config, not command output (outdated appears zero times in each). So the vendor schemas are usable as validators for mise.toml / pyproject.toml, while the structs for command output have no published schema and would have to be authored here. uv's own outdated output declares {"version": "preview"} and contains zero latest fields.
