Who Decides Done

A tool reads two sources of truth. Only one of them is allowed to say a ticket is finished — and the question is what the tool should do when they disagree.

next-ticket answers "what should I work on next" so /clear-prep never has to guess. It reads two things, and they are deliberately different kinds of thing.

The chain file

decides ORDER

21 entries, each naming an issue and the issues that block it. Committed and reviewed like any code. It has no idea what is finished — there is no done field.

The GitHub tracker

decides STATUS

Says OPEN or CLOSED for any issue. It has no idea what order anything should be worked in.

Neither alone can answer the question. That split is the whole design — and it is where the problem lives.

What the tool asks, and what it doesn't

That gap is deliberate. It is written down

"A ticket that is done is expected to be REMOVED from this file in the commit that closes it — the tool does not infer 'done' from a ticket's own tracker state, only from its blockers'." docs/roadmap/aggregated-research-chain.toml, lines 12–14

So this is not a bug someone forgot. It is a rule: the human decides done, by deleting the line. The tool is deliberately kept from having an opinion about it.

That rule worked because a person read the tool's output and would notice a ticket they knew was finished.

Then that person was removed. /clear-prep now says to "quote its output verbatim — never infer one". The reader who was the enforcement mechanism is now instructed not to think about it.

So the contract still says "the human decides done", while nothing in the loop has a human deciding anything. That is the issue.

The three ways out, and what each one moves

They are not three flavours of the same fix. They differ in who ends up deciding a ticket is done — which is exactly what the rule is about.

What the two reviewers said

The advisor first told me to skip, then reversed itself once I gave it the sentence from the chain file. Its argument for reversing: making stale entries harmless removes the last pressure that will ever exist to clean the file up — and this repository's own tools already lean the other way. Two of them refuse rather than guess: one returns nothing instead of a partial list, another refuses instead of an empty answer.

Separately, the implementing lane — which had not been told any of that — wrote into the code's own docstring that skipping the stale entry and reporting the next one anyway "would be the thing most likely" to go wrong. Two lanes reached the same place from different directions.

The honest counter-argument, which neither of them weighed. Option 1 stops your round. If a ticket is closed and still listed, you get no next task at all until you edit the file. That is a real cost paid every time, against a rot that is invisible and slow — and "the correct design" is easy to prefer when someone else pays for it.

A third advisor, given that counter-argument, picked option 3

Its answer to the cost: the stop does not actually leave you without a next task — the removal IS the next task, and option 3 puts what you are unblocking on the same screen, so the cleanup commit and the resume become one step. The price of the stop drops to near zero without the refusal being weakened.

It also refused a fourth shape I proposed — refuse on any closed entry anywhere in the file, not just the named one — on three grounds. It buys nothing, since a non-named closed entry is inert. It changes what the tool is, from "name the next ticket" into "audit the chain file", and a whole-file hygiene check belongs in a ship gate that fires at the closing commit, not in the query run at every /clear-prep. And it would hold the tool hostage to entries deep in a 21-ticket chain, several of which will legitimately close out of order.

The risk it named as deciding: option 2's failure mode is permanent and invisible — the convention dies quietly and the file becomes a second, wrong source of truth. Option 3's is a visible one-commit pause with both the fix and the payoff on screen. Choose the design whose worst case is loud and cheap.

The preview shipped, then lied, then was fixed

Option 3 is in as f82ee1c1. It did not work on the first attempt, and the reason is worth keeping, because the instruction that caused it was mine.

I told the implementer that when the entry after the stale one is also closed, the preview should chase past it — "a reader wants the real next task, not the next piece of rubbish." That sounds obviously right and it made the preview disagree with the tool. The naming rule refuses a closed entry; my preview rule skipped one. Opposite rules, so:

With [#1 closed, #2 closed, #3 open] the tool printed next after removal: #3. You remove #1, exactly as instructed. You re-run. It says STALE CHAIN — #2.

The refusal was correct both times. The promise attached to it was not.

The reviewer that caught it did so by executing the module against that fixture, not by reasoning about it — and control-armed the scope, confirming the two rules agree when only one entry is closed. The fix names what the next run will actually say, which turns out to be more useful than the chase ever was: #2 … — also CLOSED, remove it too lets you clean up both in one commit instead of discovering the second on the next run.

The mutation arms passed 9 of 9 on the code that carried this. They proved the chase step existed. They could not see that it disagreed with the rest of the module, because an arm mutates the code and asks whether a test notices — it has no way to ask whether the design was right. A clean sweep is a statement about the tests, never about the premise.

A second correction — and then a third, which withdrew it

Option 1's card first claimed "the file can never silently rot". I read the shipped code, found that the check fires only for the entry about to be named, and concluded that a CLOSED entry which still has an open blocker slips past in silence — so the enforcement was narrower than the argument for it assumed. I published that as a correction.

An advisor then refuted it, and it was right. That entry is inert. Blocker resolution reads tracker state by issue number, never chain-file presence, so a stale entry sitting mid-file contributes nothing to any output: it cannot be named, cannot mislead, cannot change what any other entry resolves to. And it is not silent forever — the moment its own blockers close, it becomes the first entry with all blockers closed, the check fires, and it is reported.

So the enforcement is deferred, not partial. Every closed entry is caught at the last moment before it could ever appear in output. The file's bytes can carry dead weight; nothing the tool says ever does.
