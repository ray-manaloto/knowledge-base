01

One graphify tree for the whole mac

“should we lift the ban on graphify? i really only want one graphify source tree for common knowledge that is relevant for all projects and coding agents on this mac. provide pros/cons and what features we lose/gain based on the graphify source tree vs global”

The ban and the goal are not actually in conflict, because graphify's global mode is not an alternative to project graphs — it is a union of them. Every project still builds its own graph.json first; global add then copies that finished graph into ~/.graphify/global-graph.json with every node ID prefixed by a repo tag.

736.4 MiB this project's graph.json alone 772,120,976 B · measured
512 MiB graphify's stock read cap security.py:32
1,024 MiB our raised cap — “a ratchet, not a fix”. But the cap is per-file, so N graphs each under it never trip mise.toml:271 · security.py:35 · #130
0.0% prefix waste today — #120 said 41% and is stale-open re-derived: max 1 rep per id, was 26

There is no “instead of” — both doors lead to the same call

graphify offers two ways in, and the second looks like the architecture you described — extract straight into the global graph, never build a project one:

  • graphify global add graphify-out/graph.json --as myrepo
  • graphify extract ./docs --global --as myrepo — the form do-not.md bans by name

They are the same thing. Read at cli.py:4256: the --global branch writes graphify-out/graph.json exactly as normal, then calls _global_add(graphify_out / "graph.json", tag) — the identical function. Global is strictly additive: a second copy layered on top, never a replacement for the per-project tree. “One source tree instead of many” is not a mode graphify has.

and its failure mode is the one this repo hunts

That same block wraps the merge in except Exception as exc: print(…, file=sys.stderr) and then exits 0. So a global merge that fails — on the cap, on a lock, on anything — leaves the extract reporting success with a warning on stderr. In a repo whose standing rules say no warning shall be dismissed, and which has already filed #438 because a stderr-is-a-refusal rule broke on a tool's own progress output, adopting global means adopting a silent-loss path.

The ban stands, and your goal is right — they are not in conflict. What you want is one knowledge surface for every agent on this mac. Global mode does not deliver it: it cannot replace the per-project trees, it prefixes specifically so projects cannot relate, it fails by stderr-and-exit-0, and do-not.md bans it as shared mutable machine state.

The two things that do deliver it are both already ticketed and neither is built: #130's federated retrieval — our own code, since lexical.py loads exactly one graph today — and #109, “knowledge-base becomes the one internal research tool.” That is where this question has been waiting since 2026-08-02.

And a 4.5 GB loose end. ~/.graphify/repos holds 79 repos. Only 11 overlap this corpus's 92 manifests — so 68 repos sit there with no manifest, invisible to every query, predating the ban. Under research-repo-enumeration.md that is an unregistered source backlog, not junk. Nobody has decided whether to register it or reclaim it.

Every function a generated wrapper type

“can we just make every function in the python library be a wrapper type that is generated by datamodel-code-generator so that we can just get this done in one swoop… is this advisable?”

“add path based and/or file type filters… or some type of deny rule… recursively under python/src/kb_setup/ and tests/”

The generator is already pinned. Nothing has ever been generated from it. codegen = ["datamodel-code-generator==0.75.1"] sits in an isolated dependency group at pyproject.toml:88, and there is no models package anywhere under python/src/kb_setup/.

1,310 defs in kb_setup — the literal blast radius of “every function” measured
462 module-level public functions measured
131 hand-written @dataclasses across 42 modules — already typed, would be replaced measured
113 test files that would need regenerating alongside measured

“One swoop” is the part that does not survive contact. A wrapper type per function means an input type and a result type each — roughly 2,600 generated classes from a JSON-Schema source that does not exist yet and would itself have to be authored by hand, function by function. The generator does not read Python; it reads schemas. So the swoop is not “run a generator”, it is “hand-author 1,310 schemas, then run a generator.”

The half that is advisable is the half already decided and never built: a base schema for common types and enums, with every other schema $ref-ing it — applied to the seams (what a mise task returns, what a gate reports, what an error code is), not to every internal helper. That is the same surface item 4's structured-output request needs, which is why these two are one project and not two.

verdict

Adopt the protocol at the seam layer — task results, gate results, error enums — where the generated types earn their keep as a machine contract. Reject it at the function layer: 1,310 wrappers is a schema-authoring project wearing a code-generation costume. The deny rule is buildable and cheap — this repo already runs five stateless PreToolUse guards, and a sixth keyed on python/src/kb_setup/** and tests/** is one more entry in the same table.

The precondition nobody has stated: a deny rule enforcing “models are generated” is unenforceable until at least one model is generated. Order matters — base schema first, one seam converted second, the guard third. A guard shipped first would deny every edit to a protocol that does not exist.

Run the numbers forward. Even at a genuinely terse 60 bytes per entry, 346 entries is 20.8 KB — 85% of the byte cap, with nothing left for the standing hazards the index exists to carry. That is exactly what has happened four rounds running (#454), and the orphan count is the receipt.

The subagent premise is refuted

The directive says: “/kb-resume is only needed for the initial prompt after /clear. i dont think it needs to be there for every subagent or subtask/fork to read.” It already isn't. Verbatim at sub-agents.md:935:

“Auto memory: the main conversation's auto memory isn't loaded [into a non-fork subagent]. To give a subagent persistent memory of its own, use the memory field.”

A subagent sees MEMORY.md only if its frontmatter declares memory: user|project|local — and then it is that agent's own ~/.claude/agent-memory/<name>/MEMORY.md, never this project's. Zero of the six roster agents declare it. So the index costs one load, in the main thread, per session. Forks are the exception and inherit by construction, which is what a fork is for.

The same page carries a second answer you have asked for repeatedly. sub-agents.md:934: a subagent runs its own system prompt, so your output style does not shape its responses either — except in a fork. That is why lane reports keep coming back in a voice you did not ask for.

corrected proposal — three moves, in this order

1. Ingest this repo's own prose — CLAUDE.md, .claude/rules/**, .claude/skills/**, docs/**. Already tracked, already committed, zero privacy question, and it is the exact content agents are instructed to obey and cannot retrieve. This is the move, and it was not on anyone's list.

2. Unblock graphify-out/memory/ — #540, the 275 work-memories, with its stated acceptance test.

3. The 346 personal topic files — last, and only if 1 and 2 leave a gap. That is where the “commit your session memory into the repo” decision actually lives, and it is a smaller decision once the first two have run.

Move 1 shares #397's precondition — kb-build must work — but nothing else. It needs no ruling from you, costs host-agent extraction on roughly 30 markdown files, and would have made all three misses above into hits.
