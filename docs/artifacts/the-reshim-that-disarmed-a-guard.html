The Reshim That Disarmed a Guard

A mise reshim wrote 836 shims at 21:28 today. Three of them are named after binaries a guard exists to say are missing — so the guard now finds them, falls silent, and denies nothing.

The suite went red on a test nothing in this branch touched. The test is right. The guard is broken. The machine changed underneath both.

The chain

Four hops, and the damage is at the last one — where a probe answers a question next to the one it was asked.

The failure mode got worse, not just unguarded

Before, an accidental timeout … died with command not found and rc 127 — an unusual code that reads as "the probe never ran". Now it dies with a mise error and rc 1, which is the single most common way for a real command to fail. The signature that used to distinguish the probe broke from the thing under test failed is gone.

That distinction is the entire reason this guard exists: it was built after a probe using timeout nearly produced a false "codex unavailable" conclusion about a paid external service.

Why the red test is the honest one

Neither the guard nor its test has been touched on this branch — both last changed on 2026-08-18, in a commit that is an ancestor of origin/main. So the suite is red on main too, and has been since the reshim, not since this work.

tests/test_absent_binary.py::test_an_introspector_behind_a_transparent_prefix_is_not_denied
AssertionError: an introspector LATER in the line must not exempt the absent binary
    assert None is not None

The test asserts that timeout 5 which foo is denied. It is not — but not for the reason the test's own comment predicts. The comment worries about the parser widening too far. The parser is fine: command_word returns all four tokens and timeout is the command word. The guard reaches its final check and finds the binary present.

A test that names one failure mode and fails from a different one is still doing its job. It is the only thing on the machine that noticed.

The blast radius is not this repo

836 shims now sit on PATH. Every one is a symlink to mise, and every one whose tool has no version set errors instead of running. Three are coreutils names this repo guards; the rest are not inventoried here.

This machine has been here before. A stale install once shimmed git, so every editor git call took a lock that never released; a shimmed node-gyp once made an install its own descendant and hung for hours at 0% CPU. Both were recorded, and both were re-armed by the same thing: a reshim that swept in a tool nobody had set a version for.

Nothing here was changed

This repo edits project settings only, never ~/.config, never global mise state. So this page reports and stops. The two shim-clearing commands the situation suggests — setting a version, or pruning the orphan — are the machine owner's call, not an agent's.
