One Graph For The Mac

You asked whether to lift the ban and keep a single graphify source tree that every project and every coding agent on this machine can read. Here is what graphify global actually does, what it would give you, and what it would cost — read from the pinned 0.9.50 source, not from the rules that describe it.

project-scoped (today) global / shared state hard blocker

First: the ban is two bans, and only one is about the graph

They are written next to each other, so they read as one rule. They govern different files for different reasons, and lifting one does not lift the other.

What global add actually builds

This is the part that decides the answer, and it is not what the name suggests. It does not re-extract anything, and it does not relate your projects to each other.

The load-bearing consequence

“One source tree for common knowledge relevant to all projects” asks for a web. global add gives a filing cabinet — N drawers in one box, and the drawers do not touch. This repo has measured that exact shape before: a cross-namespace merge produced 0 cross-namespace edges out of 815,481. That figure is inherited from a prior round's control-armed run, not re-derived this session — but the mechanism above is read from source and predicts it.

And nothing reads it by default

query.py in the pinned 0.9.50 contains zero references to global. A global graph is not automatically consulted by any query — it is reached only by pointing --graph ~/.graphify/global-graph.json at it explicitly, the same way kb-serve already binds an absolute path today. Whatever the global file gains you, “agents just find it” is not on the list; something still has to name the path.

The ledger

What lifting Ban B gains
  • One query surface. One --graph path instead of registering an MCP server per project.
  • Clean per-repo lifecycle. global remove <tag> prunes exactly one project; a re-add with an unchanged source hash is a no-op.
  • Real shared-dependency linking. Two projects using the same library collapse onto one node — genuine cross-project value, just narrower than it sounds.
  • Survives a project wipe. Deleting a project's graphify-out/ does not remove its knowledge from the global file.
What it costs
  • Reproducibility, the repo's invariant 3. The global file is derived from N project graphs at N unrelated pin states, and no manifest anywhere ties it to committed inputs. Nothing can rebuild it from source of truth.
  • Invariant 11. This repo edits project settings only. Writing ~/.graphify/ is exactly the thing it never does.
  • The Claude-only guard leaks. clean_env() is applied at every subprocess.run inside kb_setup — it is a wrapper guard, not a graphify one. A codex or antigravity agent running bare graphify against the global tree has no strip, and the machine's GEMINI_API_KEY is reachable again.
  • Memory. Every add loads the whole global graph and the whole source graph into NetworkX. This repo's graph alone is 736 MiB of JSON. The resident cost is unmeasured — but it is the whole file, every time.
  • The size cap is closer than it looks. See below.

Read this twice

On a default machine — any other project, any codex or antigravity agent — adding this repo to the global graph is refused outright: 736 MiB against a 512 MiB cap. It only works here because mise.toml raises the cap for this repo, and even then one project already occupies 72 % of it. A global graph holding this corpus plus anything else does not fit without raising the cap again on every host that reads it.

What I would do instead

Recommendation — yours to overrule

Lift Ban A's spirit, keep Ban B. The goal — one tree of common knowledge every agent on this Mac can reach — is already 90 % built and does not need the global graph.

The three moves, in order of what they actually buy:

  1. This repo is the one source tree. It already holds every shared source, pinned and committed, and rebuilds from them. That satisfies “one tree” without any shared mutable state.
  2. Reach it from everywhere over MCP, not over a shared file. mise run kb-serve already binds an absolute graph.json path — invariant 4 exists precisely so several graphify projects never collide. Registering that server in another project's .mcp.json gives that project the corpus with zero writes outside this repo and zero reproducibility loss.
  3. Keep per-platform skill installs project-scoped and automated — which is already filed as #526. That is the honest version of “all coding agents on this Mac”: each agent learns the skill in its own project, and nothing appends to ~/.claude/CLAUDE.md.

The one thing the global graph gives that MCP does not is the shared-external-library dedup. If that turns out to matter, it can be bought later by adding those upstreams to this corpus as pinned manifests — which is what sources/ is for.

What is still ambiguous

Three questions this analysis cannot settle from source, and they change the recommendation:

  • Is the goal querying one corpus from anywhere, or relating your projects to each other? MCP solves the first completely and the second not at all; the global graph solves the second only for shared third-party libraries.
  • Should the 4.7 GB already sitting in ~/.graphify/ be adopted, ingested, or deleted? It is unowned by any repo and four months stale.
  • Does “all coding agents” include agents in projects that are not this one and not dotfiles? That is the case where the 512 MiB default cap bites.
