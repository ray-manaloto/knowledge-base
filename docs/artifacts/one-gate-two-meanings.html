Security gate · found 2026-08-25 · issue #506

One Gate, Two Meanings

Commit one file and the secret scanner reads that file. Commit two and it reads fifty megabytes of your working tree instead — including everything git is configured to ignore. Same gate, same config, different question.

How it was found

Not by looking. By two commits disagreeing about the same gate.

A one-file commit passed. A nine-file commit, minutes later on the same tree, was refused for a secret in a scraped web page that nobody was committing — a gitignored Firecrawl cache. Two probes of one gate, two answers. One of them had to be broken.

The mechanism is a single line of CLI grammar. gitleaks dir takes one path — its own usage is gitleaks dir [flags] [path] — and silently ignores extra positionals, falling back to the current directory. The hk builtin hands it the whole file list sources/hk/pkl/builtins/gitleaks.pkl:17.

The three arms

One path, two paths, and the repo root — the third is what makes it a finding.

$ gitleaks dir --redact --no-banner manifest.py scanned ~20,490 bytes $ gitleaks dir --redact --no-banner manifest.py test_manifest_add.py scanned ~49,957,227 bytes $ gitleaks dir --redact --no-banner . scanned ~49,957,227 bytes <- identical. the paths were discarded.

Two paths and the repo root agreeing to the byte is the whole argument. A tool that merely widened its scan would not land on exactly the number you get by naming no path at all.

The last row is the one to hold on to. This was never a hole; every staged byte was read. What leaked was attention — a gate that cries on other people's junk is a gate people learn to route around.

The repo already knew, and I didn't check

hk.pkl:24-35 and :79-97 record this behaviour, measured on 2026-07-28: “gitleaks dir IGNORES its path arguments once there is more than one (measured: 1 arg → 5.01 KB scanned, 2 args → 8.62 MB).” The figures on this page are an independent re-derivation at today's tree size, not a discovery, and the commit that fixed the pre-commit half does not cite that prior art. The implementer lane caught the omission; recording it here is the correction.

Those same comments are explicit that the whole-tree scan was a hazard they refused to rest on, not a feature: “a gitleaks release that starts honouring its args would have silently removed the only tool coverage these paths have.” Which makes the fix below the controlled version of the exact event they were bracing for.

The fix, and whose idea it was

Not an invention — gitleaks ships the answer in its own hook definition.

# sources/gitleaks/.pre-commit-hooks.yaml entry: gitleaks git --pre-commit --redact --staged --verbose pass_filenames: false <- it asks NOT to be given filenames

hk's builtin cites that very file — builtins/gitleaks.pkl:14 references .pre-commit-hooks.yaml#L4 — and line 4 is the git --staged entry. It quotes the line that says don't pass filenames, then passes filenames.

--staged scopes the scan to what is actually being committed, so gitignored paths are excluded by construction — no second list beside .gitignore to drift.

arm — same secret, same file, same treerc
planted token in a staged tracked file1 — still catches real leaks
same file cleaned and restaged0
planted token in a gitignored file, old shape1 — control: it is detectable
planted token in a gitignored file, new shape0 — the point

The third arm was added because the fourth was vacuous. The first draft planted a bare token with no key = "…" context, which the rule does not match — so the old shape didn't flag it either, and the “pass” proved nothing. A control arm that cannot produce the other answer is not a control arm.

And because hk.pkl calls that coverage load-bearing, it was checked rather than assumed, with this repo's real .gitleaks.toml copied into the fixture: a token staged under graphify-out/memory/ → rc 1; under docs/research/ → rc 1; a clean file → rc 0. Coverage survives, and is now deterministic rather than accidental.

Half fixed, and the half that isn't

The pre-commit hook is done. check and fix still run the builtin, so mise run lint is still red on this finding — and it cannot simply take the same command, because check --all has nothing staged. --staged there would be a gate that can only pass, which is a worse defect than the one being fixed.

The open question is how to scope a whole-tree scan without copying .gitignore into a second list. Tracked in #506; the option that fits this repo's own doctrine is to generate the allowlist from .gitignore and gate it with a byte comparison, the way the existing codegen checks work.

Provenance

  • Every byte count was measured on this repo this session. 20,490 / 49,957,227 / 49,957,227 come from three consecutive runs differing only in their positional arguments.
  • 19,972,251 tracked bytes is the sum over git ls-files, not an estimate.
  • The four arms ran in a throwaway git repository, never against this checkout, so no index belonging to a running lane was touched. The load-bearing-coverage arms used a copy of this repo's real .gitleaks.toml.
  • No secret value was read or printed at any point. The 24 findings were characterised by rule id, count, and a SHA-256 digest of the matched string — 24 findings, one distinct value, prefix AKIA, length 20, not one of AWS's published examples.
  • Not measured: whether a newer hk has changed this builtin, and whether gitleaks documents the multi-argument behaviour as intentional. Both are due diligence owed before anything is filed upstream, and neither has been done.
