Why kb-build Is Red

Not a graphify bug. Not the stderr policy. A source manifest whose author wrote “extraction deferred” in a comment and never set the key that defers it.

The shape of the defect

A comment is prose. The parser reads keys.

sources/ast-grep.manifest carries only url, ref, commit, kind — verified this session. Its comment says extraction is deferred; no build key exists, so it defaults to include and the build extracts it anyway. codex.manifest:53 sets build = skip and is correctly excluded, which proves the mechanism works and was simply never reached for.

Timing corroborates: manifest added 2026-08-27, first build after it failed 2026-08-29T21:33:55Z.

The thing that will bite next

One more is already broken, and the class is exactly three

Commit b2d51b53 (“bump five patch-level CLI pins”) bumped six manifests and touched graph.py zero times — both measured this session. But graph.py registers a content hash for a source's Cargo.toml, and a bump invalidates it.

Corrected after publication — I published “three” and the real number is 14. I counted the three named *_MANIFEST_PATHS constants and treated that as the registry. It is not: _EXPECTED_METADATA_ONLY (graph.py:266) holds 22 registered files across 14 distinct sources — 10x-Team, Attacca, cclint, code-review-graph, datamodel-code-generator, graphify, logbook, OpenSymphony, pensyve, picologging, ruff, taplo, typos, uv — and every one of them has a bumpable sources/<name>.manifest, checked individually. The three constants were a proxy for the registry, and I measured the proxy.

The systemic version: fourteen sources have a pin that lives in two files — the manifest and graph.py — with no gate enforcing they move together. This repo already knows this shape: sources/graphify.manifest warns in its own comments that its pin spans two files and "must move in the same commit". Same trap, fourteen more pairs, no guard. That is a gate worth building, not fourteen hashes worth hand-checking.

Correction

A premise I gave the lane was wrong, and it was my own display bound

I told the lane six sources carry a Cargo.toml, naming them. The real number is 34. I had run the search piped through head -6 and reported the first six as the complete set — a display bound reported as a finding, which is the exact failure this repo has a written rule about. The lane dissented against the premise and found the real culprit, which was not among my six.

Worth stating because the premise block exists precisely to stop this, and it did not: the row was cited and measured, and still wrong, because the command was bounded before the citation was taken.

And it happened twice in one session. The second time I counted three named constants and called that the registry, when the registry holds fourteen sources (corrected above). Different surface, identical error: I measured a proxy for the thing instead of the thing — once a truncated list, once a convenient variable name. Both read as measurements, and both were published before anyone checked.

What to do

Two edits, neither of them in graphify

  1. sources/ast-grep.manifest — add build = defer (or skip) with a reason, matching what codex.manifest already does. Or, if it is wanted in the corpus now, register its Cargo.toml as expected-metadata-only.
  2. python/src/kb_setup/graph.py — refresh the uv Cargo.toml hash before the next build, or it fails there instead.
And when the build is finally run: set GRAPHIFY_NO_BACKUP=1, or a successful run writes another dated snapshot of roughly 778 MB beside the one already there. Nothing rotates them.

A plain re-run will not fix this. graphify's warning says empties are retried, but this is a deterministic structural zero-node result, not the transient it describes — so the message's own advice is misleading here.
