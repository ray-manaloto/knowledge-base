Why kb-build Is Red

Not a graphify bug. Not the stderr policy. A package manifest that produces zero nodes and was never registered as expected — and it was never one manifest. It is a class of eleven, of which exactly one is still unguarded.

Update — the build was run, and failed again. The two edits this page originally prescribed were made. mise run kb-build then ran to completion and failed at 2026-08-31T12:15:42Z with the identical error on a different source: biome. Fixing one instance let extraction reach the next.

That reframed the finding as a class — and the first attempt to size that class was wrong in the alarming direction. It reported 34 Cargo.toml files with “the rest unaudited”, implying an open-ended queue of red builds at ~55 minutes each. The audit takes about thirty seconds and the queue has one item.

What to do — revised after the second failed build

One edit unblocks the build. One gate stops the class.

The two edits this section originally listed were made, and the build failed anyway. Their replacement is not a third edit of the same kind.

  1. sources/biome.manifest — give it a build key, or register its Cargo.toml hash. The audit above says this is the last one, so unlike the previous two this edit has a green build behind it rather than another name.
  2. A gate that runs the audit without a build. Enumerate every source's bare package manifests and require each to be excluded or registered. It takes seconds; discovering the same fact by building takes about 55 minutes and yields exactly one name per run.
That gate has a second job already waiting for it. Fourteen sources carry a pin in two files — the manifest and graph.py — with nothing forcing them to move together, which is the defect in the section above. Registration-coverage and hash-freshness are the same check asked at two moments, so one gate answers both findings.
And when the build is run: set GRAPHIFY_NO_BACKUP=1, or a successful run writes another dated snapshot of roughly 778 MB beside the one already there. Nothing rotates them. Until a green build exists, the existing 778 MB snapshot is the only near-copy of a graph this repo cannot currently rebuild — so it stays.

A plain re-run will not fix this. graphify's warning says empties are retried, but this is a deterministic structural zero-node result, not the transient it describes — so the message's own advice is misleading here.

Correction · third

“The rest are unaudited” was a guess wearing a measurement's clothes

After the second failed build, the finding was written up as an open-ended queue: 34 Cargo.toml files exist, 14 sources are registered, the rest are unaudited — and the explicit advice was do not fix biome and re-run, because each build buys only one more name. Every number in that sentence was real. The conclusion drawn from them was not, because nobody ran the audit it was recommending.

Running it costs about thirty seconds and closes the set: 475 files, 462 with a [package], 11 bare, 2 unparsable, and 10 of those 11 already excluded or registered. The queue was never open-ended. The advice inverted as a result — fixing biome is now the cheap path to a green build, not a wasted 55 minutes.

This is the same failure the section above already records twice, at a larger scale: a head -6 reported as a population, three constants reported as a registry, and now an unrun audit reported as an unbounded tail. Each time the error was reasoning outward from a partial measurement instead of completing it. The control arm that broke the pattern here was an accident — uv was chosen as the “has a real [package]” control and turned out to be just as bare as biome, which is what exposed that the file's shape was never the discriminator at all.
