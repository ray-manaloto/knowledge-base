The one module that prints

Both were decided long ago and built — a 12 KB selection report, six candidates evaluated, structlog chosen, 647 lines of event and sink code, eleven modules emitting. The research CLI is not one of them. It is the only piece heading to another repo, and the only piece still using bare print.

What already exists

Your own ruling, 2026-08-09, quoted in the code: "one structured event stream with a human-rendering stdout sink" — explicitly not "reports become log lines." Most of this repo's ~455 print sites are the product: `kb-check`'s summary, `kb-gates`' report. They became events; a sink renders them as the text read today.

The library was chosen on evidence, not preference. `docs/research/reports/2026-08-10-logging-library-selection.md` evaluated six ingested candidates. structlog owns the event layer; stdlib owns the sink layer — the decisive axis, because whoever owns the sink owns the shape of every report this repo prints.

And there is already a JSONL surface. Set KB_EVENTS_JSONL and every event is also written one JSON object per line. Off by default, so ordinary runs print exactly what they print today.

Where the research CLI sits

"Structured output" is three different things here

built
The result — one JSON record per adapterAdapterRecord, generated from schemas/research-record.schema.json with a drift gate. JSON is the only output format; no --json flag, by an advisor ruling. This is the piece that was already right.
decided, unused
The logs — a structured event streamstructlog + a stdlib sink, chosen on a six-candidate evaluation, with an opt-in JSONL surface. Eleven modules use it. The research CLI does not, and it is the one going somewhere the modules cannot follow.
open
The model's output — schema-constrained generation in the spineThe spine dispatches to model lanes and takes back claims, votes and a synthesis. Whether those are schema-constrained or parsed from prose has never been decided. It rides with the spine, which is deferred to a prototype.

Why this is worth a decision now, not later

Rung 5 is a one-way door for this. Once the CLI is its own package in another repo, converting it to the event stream means either vendoring events.py/sinks.py, depending on kb_setup from the new package — reintroducing the coupling rung 5 exists to remove — or writing a second, smaller event layer that will drift from this one.

The cheap moment is before the split, while both still live in the same package: convert research/ to emit, decide what travels, then move it. That ordering is a spec decision and it belongs in the ticket for rung 5, not discovered during it.

It also touches something already on record: the per-call telemetry deleted with the semantic-corpus layer, which you have asked to have back. An adapter emitting structured events with timings and outcomes is the same surface.
