The Lockfile Blind Spot

Seven gates went green on a commit that could not have merged. Every gate was honest. None of them read the file that was wrong.

A version pin lives in four places

Bumping a tool is not one edit. It is four edits that must agree, and the tools that check them do not all read the same files.

This repo pins its CLI tools in mise.toml. But a pin has three companions: mise.lock holds the per-platform download URL and checksum for every platform (not just this Mac), sources/<tool>.manifest pins the upstream tag the corpus is built from, and currency.toml records what the drift engine expects to see.

What made this invisible

The verification I ran was correct. mise ls --current confirmed all five new versions were genuinely installed, which rules out the vacuous-green failure it was chosen to rule out. It just answers a different question than “is the lockfile consistent?” — and no gate in the bundle asks that one.

The probe that did find it, and its control arm

mise lock --dry-run --json reported exactly the five bumped tools as pending movement. Run against hk, gh and python — pins this change never touched — it returned []. A probe that returns both answers is evidence; one that has only ever returned the alarming answer is not.

The first fix was worse than the bug

A bare mise lock regenerates everything it can reach. What it reached included a dependency closure this change has no business touching.

Expired, or merely solvable?

The second finding was an error in my own instruction, not in the code the lane wrote. The word I chose was wrong, and the wrong word would have outlived me.

A comment in currency.toml explained why the ctx7 tool has no upstream version check: the repo it comes from publishes two differently-versioned things, so a naive tag lookup returns the wrong one. Upstream has since started publishing ctx7@<version> tags, so I told the lane the old reasoning had expired.

Why the distinction is load-bearing

A comment saying a hazard expired is a comment that stops anyone from checking. The mechanism that solves it — tag_prefix — is a real field (config.py:199, consumed at upstream.py:572-574) already declared in the block immediately above this one. So the honest comment does not close the question; it hands the next reader a two-line fix and says why this change did not take it.
