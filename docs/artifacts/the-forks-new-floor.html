The Fork’s New Floor

We keep seven patches graphify itself does not have. Upstream released a new version, so the seven had to be lifted off the old floor and set down on the new one — without losing a single one.

Imagine you built seven rooms onto a house that sits on rented land. The landlord replaces the land underneath you with a newer, better plot. Your rooms don’t automatically come along. You have to lift them off, set them down on the new ground, and then walk every room to check nothing was left behind.

That is a rebase. The land is graphify’s official release. The seven rooms are our own commits — the ones that teach graphify to talk to the Codex CLI. Nobody else has them, so nobody else will carry them for us.

The whole job is: move seven, lose none, and be able to prove none were lost.

What moved

The old floor was release v0.9.49. Since then upstream shipped 17 commits and cut v0.9.50. Ray named that exact commit as the new floor. Our seven were replayed one at a time onto it.

The one thing that clashed

Upstream wrote a 0.9.50 section at the top of the changelog. One of our commits had renamed the same heading to ## Unreleased. Git could not guess which one we wanted, so it stopped and asked.

The resolution keeps both: upstream’s changelog verbatim, with our entries carried above it under ## Unreleased. That also quietly restored 25 lines of upstream’s 0.9.49 notes that the fork had deleted by accident when it renamed the heading.

How we know nothing was lost

Here is the trap. After a rebase, the code looks fine and the version number reads 0.9.50 — exactly what plain upstream reads. The version string cannot tell you whether our patches survived. It never could; it moves when upstream releases, not when we patch.

So the check has to be a test that can come back both ways. Four test files ship with our seven commits. Run them against our rebased fork — they should pass. Run the identical four against plain upstream, with none of our patches — they should fail. If they pass in both places, the test is measuring nothing.

A second, independent check backs this up: the code the seven commits add is the same size before and after the move. Diffing old‑base‑to‑old‑tip against new‑base‑to‑new‑tip, with the changelog excluded, gives an identical line count. Nothing was dropped in the replay.

New this session, and it changes the fork’s status. The upstream pull request that would have made this fork unnecessary — #2981 — is now closed without being merged. Upstream v0.9.50 still contains zero mentions of openai-cli (control arm: 23 mentions of claude-cli in the same file, so the search works). The fork is no longer a temporary bridge waiting for a merge. It is where this capability lives.

The last step, and why it waited

The rebase is done and pushed, the MCP fix landed on top of it as an eighth commit, and the pin has now moved with it. That last step was held back deliberately until the fix was in: the pin lives in eight places and they have to move in one commit, or some surface keeps describing code we no longer run.
