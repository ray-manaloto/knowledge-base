Issue #397 · measured 2026-08-27

The gate that fails closed

Eleven of eighty-six sources stop mise run kb-build dead. Fifty-six files are the reason. Three different doors lead past them, and they are not equally sized — one of them was never on the table when the mechanism was chosen.

What actually happens today

Run the build and it gets all the way to detection, then refuses to write anything at all:

[kb-build] 86 source(s)
Graphify detect preflight failed for 11 source(s);
categories={timeout: 1, unclassified-files: 10};
no aggregate artifact or stamp was mutated

That last line is the whole problem. The gate is all-or-nothing: fifty-six files nobody wants in the graph anyway block eighty-six sources from producing one. The ticket blamed anthropic-sdk-python and ref = main; that manifest now pins v1.0.0 and no longer appears. #397's body is stale — this is the current, re-measured failure.

The fifty-six, sorted by what they are

Not one of them is a per-repo oddity. Every single one belongs to a file class — a name shape or an extension that will recur in the next source, and the one after that.

Where the refusal is decided

Detection does not run against the pinned clone. It runs against a disposable snapshot cloned fresh at the verified commit, and that snapshot is checked for drift before and after. Everything that happens to a source passes through this spine:

The three doors — and where each one cuts in

The routes differ by where on that spine they intervene, and that single fact is what decides the cost of each.

The routes, priced

Route A

.graphifyignore written into each snapshot

A new manifest field lists paths; kb_setup writes them into the snapshot after fetch. This is the mechanism the last session recorded as settled.

  • Needs a manifest field, a parser change, a writer, and a widening of the snapshot drift allowance so its own file is not read as tampering.
  • The path list is still per-source and still hand-written — 56 entries, spread across 10 manifests.
  • The next source with a PRETTIER_LICENSE blocks the build again and needs its own entry.

cost ≈ 4 code changes + 56 data entries · recurring per new source

Route B

Widen the classifier this repo already owns — recommended

kb_setup.graphify_sdk.classify_unclassified() already sorts detector leftovers into non-source, unsupported-language and unresolved, and only the third blocks. Every one of the 56 fits a class it nearly has.

  • Roughly seven rule additions: widen the LICENSE match past its anchor, add an *rc shape, add the binary and grammar suffixes, add the marker names.
  • Fixes all 10 sources in one edit, and pre-empts every future source with the same file shapes.
  • Admission stays structural — a path only leaves unresolved if it resolves to a real regular file inside the tree. That containment check is untouched.

cost ≈ 1 module + its tests · no per-source data · no recurrence

Route C

Per-source reviewed inventory entries

The existing ExpectedUnclassifiedFile path: one reviewed, content-hashed entry per file. Maximum auditability, maximum labour.

  • 56 entries by hand, each with a SHA and a stated reason.
  • This is exactly the cost that made #409 skip two sources outright rather than write 94 and 233 entries.
  • Every upstream bump that changes one of those files invalidates its hash.

cost ≈ 56 hand-written entries · recurring on every pin advance

Why this is a question and not just work

The recommendation that was overridden was labelled “the fork's classifier”. Route B is not that. classify_unclassified lives in python/src/kb_setup/graphify_sdk.py — this repo's own absorption layer, sitting on top of graphify. Changing it touches no fork, no vendored code, and no pin.

So the option now on the table may never have been the one that was rejected. That is the only reason the settled mechanism is being reopened rather than executed — and it is being reopened once, here, not re-litigated later.

Out of scope, deliberately

ffmpeg fails on a detect timeout, not on unclassified files. That is the sixth case in #491, which the last round settled as defers, does not close. It stays deferred; unblocking the other ten is what #397 is.

The ref = main half of #397 is now #546 and is untouched here.

Outcome — added after publication

Route B was chosen and executed the same session. Nothing above was removed; this is what happened next.

Detect preflight went from 11 failing sources to 0, across all 85 built sources. Five rule edits in graphify_sdk.py plus one in graphify_health.py. No fork, no manifest data, no per-source entries.

The A premise held for 10 of the 12 undisplayed paths. The two it missed were gh's script/distributions and script/override.ubuntu — Debian/APT packaging tables, read and then classified as counted rather than guessed at.

ffmpeg is now build = defer citing #491: a detect timeout, which no classifier rule reaches.

One thing this page got wrong by omission: it framed the 56 files as the whole blockage. They were the whole of detection. Past that gate, kb-build now dies in extraction instead — ast-grep's Cargo.toml produces zero nodes (upstream graphify #1666) and one .d.ts extracts partially. That is #417's family, with its own ruling and its own cost, and it is filed rather than absorbed here.

So #397's blocker is fixed; #397's acceptance criterion 3 — “kb-build completes and writes the stamp” — is not yet met, and is blocked behind #417. Stated plainly because a green preflight reads like a green build, and it is not one.
