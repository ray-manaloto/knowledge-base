Eight Files, One Table

Four schemas were fed to a code generator by eight hand-written Python files. The generator already shipped both halves of what they did. Deleting them found a trap none of us knew was there.

Each of four JSON Schemas had a generate_X.py that shelled out to datamodel-codegen, and a check_X_codegen.py that generated to a temp directory and compared bytes. Every one of the four passed an identical flag list. The generator ships --all-jobs, which reads named jobs from pyproject.toml, and --check, which exits 1 on a difference. Both halves already existed.

What actually changed

Before and after

The trap: a convenience that only fires on one path

Converting the config produced four models that parsed fine and had lost every constraint. Not a formatting difference — Annotated[int, Meta(ge=0)] collapsed to a bare int, across all four models, silently.

Why it did not ship. The acceptance criterion was not "the config looks right", it was generate every model and confirm git status reports nothing changed. A byte-identity criterion cannot be satisfied by a plausible-looking config. The mechanism was then read out of the installed source rather than guessed at.

Which key actually carries it

The comment written to record that trap said the constraints drop "unless these are named here" — naming both use-annotated and field-constraints. Half of that was wrong, and a mutation arm is what said so.

  1. Drop field-constraints alone and expect the drift gate to catch it. It survived — the gate saw nothing.
  2. Split the arm. Drop both keys: died. Drop use-annotated alone: died.
  3. So use-annotated is the load-bearing one — it is what enables field-constraints, which does nothing on its own. The comment now says that, and cites the arm ids that measured it.

The shape worth remembering. This was a comment defending a choice, written by the person who had just made it, at the moment they understood it best. Nobody re-reads a comment they agree with. It took an arm that was expected to pass — and did — to expose it.

Two couplings, written down rather than rediscovered

Generated bytes depend on the output path

The generator runs its formatter with the working directory set to the job's output directory, and the formatter discovers its config by walking up from there. So the same generator, same flags, same schema, produces different bytes depending on where the output lives.

This is why the first probe of the change lied. Generating into a scratch directory outside the repository produced 88-column wrapping against the committed 100 — which read as "the native path cannot reproduce this". Re-run with the output inside the tree: byte-identical. A probe with a bound that changes the answer.

It also retroactively condemns the deleted checkers: generate to a temp directory and compare is structurally wrong under this coupling. It only ever passed by coincidence. The native --check compares in place.

The drift gate cannot see a formatter rewrite

Generation and checking run the same formatter pass. That has a direction it cannot fail in.

What proves it

The acceptance criterion asked for the fail direction to be shown per job. Six mutation arms plus a control, run through the repository's own harness rather than a hand-written loop.

A seventh direction, which no stale/restore cycle can see. Generate cleanly, then run the repository's own formatter over everything, then re-check. Result: 220 files left unchanged, gate rc 0, tree clean — the generator's output is a fixed point of the repository's formatter. The first attempt at this probe was a no-op: the formatter's fix path is scoped to files git reports as modified, so on a clean tree it formatted nothing and could not have detected anything.
