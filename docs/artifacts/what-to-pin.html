What To Pin

Two codex lanes researched the state machine library and the DBOS pin set. Both came back with a clear answer. Then a resolve I ran myself found a cost neither of them reported.

The proposal — two lines 
# in [project].dependencies, as FLOORS, per pyproject.toml:20-24
  # Durable workflows + the bundled dbos CLI. SQLite system DB is in the base package.
  "dbos>=2.31.0",
  # States.from_enum() consumes our generated StrEnum; async callbacks native.
  "python-statemachine>=3.2.1",

Nothing goes in mise.toml. Both are Python libraries, and the dbos CLI ships inside the same wheel — a mise entry would create a second installation and a second version surface for one tool.

Both resolve cleanly on Python 3.14. I verified that myself rather than taking it from a report; the lane could not, because its sandbox had no DNS.

The finding neither lane reported

You get PostgreSQL whether you want it or not

The design wants SQLite. The DBOS lane established — correctly, and from the released 2.31.0 tag rather than main — that SQLite is fully supported and needs no extra. All true.

But a dependency tree is not a configuration. I resolved the two lines against Python 3.14 and read what actually arrives.

What this does and does not mean

It is not a blocker. psycopg installs fine and is simply never imported when the system database URL is a sqlite:/// one. Nothing breaks.

It is a cost worth naming before we pay it: two packages, one of them a large compiled wheel, in every environment and every lockfile, forever, for a database this design does not use. If that is unacceptable, the honest alternative is the no-library option below plus a hand-rolled durable-step wrapper — which is more code and less recovery, and I would not recommend it for this.

Proposal 1 · the state machine

python-statemachine>=3.2.1

Six candidates were scored against your requirement in order: does it accept an enum it did not define, then Python 3.14 metadata, then native async, then persistence. Only one row satisfies every hard axis.

Why this one

  • States.from_enum(GeneratedState, use_enum_instance=False) takes our generated StrEnum and leaves it external — exactly your requirement, and the axis that eliminates three candidates.
  • use_enum_instance=False stores the raw string in the row, which is the safer SQLite boundary than a pickled enum instance.
  • Async callbacks and guards are native, so a step can await without a shim.
  • Ships an official SQLite-backed model example, so the persistence hook is documented rather than inferred.
  • Released and last-committed 2026-08-01; 9 open issues.

What it costs, and the risk

  • A new direct dependency where the repo’s standing rule prefers a few lines of our own.
  • Two configuration choices must be made deliberately or the defaults bite: use StateMachine, not the StateChart error policy, and keep catch_errors_as_events=False so a callback failure propagates to the DBOS step instead of being swallowed as an event.
  • The one risk that would change this: no upstream source documents the full combination — our generated StrEnum + Python 3.14.7 + a SQLite row + DBOS retry/replay. That is an integration probe nobody has run, and it should be the first task of whatever ticket adopts this.

Proposal 2 · the workflow engine

dbos>=2.31.0, and nothing in mise.toml

Correction — I told you the opposite earlier

I said DBOS defaults to PostgreSQL and that SQLite would be the hard part. That is false for the released 2.31.0. SQLite is the default system store — the config reference defaults the URL to sqlite:///[application_name].sqlite when none is given. PostgreSQL is the production recommendation, not the default.

The proof is in the released tag, not on main: dbos/_sys_db_sqlite.py exists at 2.31.0 and defines SQLiteSystemDatabase. That distinction mattered — an earlier lane found #638 had cited a “merged SQLite PR” that does not exist, so main-only evidence was not going to be good enough.

Why the line is what it is

  • No extra needed. The synchronous SQLite system database is in the base package; Python’s own sqlite3 driver serves the sqlite:/// URL. Control arm: the same probe does find the real otel and validation extras, so it can see extras that exist.
  • aiosqlite is a different thing — it is for an async application datasource (sqlite+aiosqlite:///), not the system store. Add it only if we adopt that, and then replace the line rather than adding a second.
  • Nothing in mise.toml: the dbos CLI (dbos migrate, dbos workflow, dbos start) is a console entry point in the same wheel.
  • A floor, not an exact pin — house style, and no DBOS-specific reason to make it an exception.

What it costs

  • Seven new packages, including the two PostgreSQL drivers above.
  • SQLAlchemy arrives as a hard dependency. That is fine but it is a large surface, and it means the schema’s DDL will in practice be written through SQLAlchemy rather than raw SQL.
  • use_listen_notify must be false with SQLite — a documented constraint that will bite whoever configures it if it is not in the ticket.
  • End-to-end install on 3.14 is proven only as far as resolution. I resolved it; I did not install it. A clean-environment install is the honest next arm and belongs in the adopting ticket.

The conflict both lanes surfaced independently

Every floor-pinned dependency is invisible to our own currency engine

This started as my error — I wrote a spec premise saying this project pins exactly. A lane refused the spec and cited pyproject.toml:20-24, which says the opposite. It was right. But correcting it exposed something larger.

The house style is a floor — “an exact pin here is exported as someone else’s constraint. Reproducibility for us is uv.lock.”pyproject.toml:20-24

dbos:        ('', ())        <- what our new floor would be
Why this is the most useful thing on the page

An earlier lane measured that 15 of 33 direct dependencies have no currency mapping and reported it as a coverage gap. This is the mechanism. Three of those fifteen — anthropic, httpx2, structlog — are unmapped for exactly one reason: they are floors, and the parser only recognises ==.

My recommendation, and the lane reached it independently: change the engine, not the policy. Treat the presence of a floor in [project].dependencies as proof the project owns the dependency, then read the concrete resolved version from uv.lock. That keeps the consumer-safe exported floor and gets the real version from the file that already carries reproducibility.

The alternative — pin == just to satisfy the parser — exports a hard constraint onto every downstream consumer to work around our own tooling. That is the tail wagging the dog, and it is what I would have unknowingly recommended if the lane had not refused my spec.
