Two rules, opposite answers

Both load every session. One forbids exactly what the other permits.

The strict one

Only add an outside tool if its setting stays inside this project. Never one that writes into your machine’s shared settings.

do-not.md

The lenient one

If a tool needs it, adding it is fine — even into the shared settings. This is a preference, not a rule.

research-doc-sources.md

What happened when the lenient one was followed

Adding a tool wrote into the machine’s shared settings. That clashed with this project’s own entry for the same tool, and codex stopped working entirely — not degraded, refused to start.

→ Which one wins?

If the strict one wins, a tool that can only install itself into shared settings is a tool we turn down. If the lenient one wins, that clash can happen again, so we’d need a check-before-adding step. There is a middle option: strict by default, and you decide the exceptions.
