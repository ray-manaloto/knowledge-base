Aggregated Research, Assembled

Every component, what it is, what it depends on, and the exact path one question takes through all of them. Nothing here is installed yet except what is marked as already present.

aggregated-research stops being a skill in this repo and becomes a plugin — one that composes tools it does not own. It ships the ordering, the control-arm discipline and four new wrappers; it declares the search surfaces as dependencies rather than vendoring them.

That composition is possible because the marketplace schema supports it, which was the fact that settled the design: plugin.dependencies — “Plugins that must be enabled for this plugin to function” — plus allowCrossMarketplaceDependenciesOn, “marketplace names whose plugins may be auto-installed as dependencies. Only the root marketplace's allowlist applies — no transitive trust.”

Why four new wrappers and not four new plugins

Three of the four have no Python library to wrap — measured: grep.app has zero PyPI packages, deps.dev has two community packages both effectively unmaintained, and Chroma's Package Search is absent from chromadb. Only lychee ships anything, and what it ships is the binary itself (lychee-bin 0.24.2 on PyPI). So each is a small module in one package, sharing this repo's existing Ok/Err/External result type — not four dependencies, and not four plugins.

One question, end to end

The sequence below is the real path, in the real order, for a question with no primary source — the hardest class. Each rung can end the whole thing: stop at the first one that answers.

The mechanism worth copying, now known

The /deep-research lane landed. Its script is embedded verbatim and unminified in the Claude Code binary, and its own header comment states the architecture in one line: 

// deep-research: Scope → pipeline(Search → URL-dedup → Fetch+Extract)
//                → 3-vote Verify → Synthesize
// Ported from bughunter architecture. WebSearch/WebFetch instead of git/grep.

const VOTES_PER_CLAIM      = 3
const REFUTATIONS_REQUIRED  = 2
const MAX_FETCH             = 15
const MAX_VERIFY_CLAIMS     = 25

And the tally is three-outcome, not binary. That is the part worth copying, and it is the same rule this skill already enforces one level up — an infrastructure failure must never read as an answer:

outcomeconditionmeaning
survivesvalid ≥ 2 AND refuted < 2a quorum of votes actually landed, and they did not kill it
refutedrefuted ≥ 2adjudicated against on merit
unverifiedtoo few VALID votesthe verifiers errored — never reported as refuted

Its verifier prompt is adversarial by construction — “Be SKEPTICAL. Try to REFUTE this claim. Default to refuted=true if uncertain” — and all three buckets reach the output, with the synthesizer explicitly handed the refuted and unverified lists and told to name the unverified count in its caveats.

Its agents get exactly two tools: WebSearch and WebFetch. Nothing else is named in any of its five prompts. So its breadth is wide and its depth is shallow by design — it never reads source at a pinned ref, never checks whether a tracker channel exists, and never touches a local corpus. Those are the rungs our ordering adds, and this settles that the two are complements rather than substitutes.

And it is unreachable by any agent, by design

The registration carries disableModelInvocation, which resolves true unless an account feature gate is on. The Skill-tool check keys on userTypedThisTurn, not on whether you are the main session — and the refusal message says so in words: “It cannot be invoked via the Skill tool in this session, by the coordinator or by workers.” Workers are subagents.

So the earlier finding was right for a reason nobody had read: only a human typing /deep-research unlocks it. The skill asks the user; it does not plan around running it.
