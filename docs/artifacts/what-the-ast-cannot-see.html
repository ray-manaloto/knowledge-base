What the AST cannot see

Why scanning this codebase for “which function reads which config file” finds two answers, and what a type-aware language server would do differently.

A tool ran over the whole kb_setup tree looking for edges of the form this function reads that file. It found 2.

Not two hundred. Two. And that is not a bug — it is the precise shape of what a syntax tree can and cannot know.

The code it was looking at

This pattern, or something like it, is everywhere in this repo:

def load_all(root: Path) -> list[Manifest]:
    out = []
    for p in root.glob("sources/*.manifest"):   # the filename lives HERE
        out.append(load(p))
    return out


def load(path: Path) -> Manifest:
    raw = path.read_text()               # the READ happens HERE
    return parse(raw)

The filename and the read are in different functions. Nothing is wrong with that — it is good design. But it is what makes the edge invisible.

So they are not competitors

The instinct is to ask which one to use. That is the wrong question: they answer different questions and fail in different directions.

That last row is the one that matters. An AST pass that cannot resolve something produces no edge and says nothing. A language server asked a question it cannot answer returns an empty result you can see. One failure mode is invisible; the other is a data point.

The AST layer is not just incomplete — it is measurably lossy here

Three separate measurements, all of them boundary failures:

43% of kb_setup's functions are absent from the graph entirely, because a private _foo and a public foo normalise to the same id and every one after the first is silently dropped. A specific node — _build_checked — vanished from a generated diagram, the node itself, not merely its edges. And 2 config-read edges across the whole tree, for the reason drawn above.

All three are the same class: something that needed a wider scope than one file, one function, or one name.

What makes this newly practical

ty is Astral's Python type checker. It is already pinned in this repo at 0.0.74, and it already runs here every time mise run lint does.

What was not known until today is that ty server ships the two capabilities this needs, natively — read from its own shipped source, not from a docs page:

call_hierarchy_provider · type_hierarchy_provider · workspace_symbol_provider

Call hierarchy landed in ty 0.0.41; type hierarchy in 0.0.20. The pin here is 0.0.74 — both are already present in the binary this repo installs.

So the missing capability is not a dependency to add or a tool to evaluate. It is a client: something that starts the server, asks it those questions, and turns the answers into edges. That is the only piece that does not exist.

One correction to a decision already recorded

A 2026-08-24 review rejected the LSP path with this reason: “python-only, needs a live server, strictly weaker than the AST graph we own.”

The first two clauses are still true and are real costs. The third is refuted by the three measurements above — the AST graph is not the strong baseline that reason assumed. And the rejection covered generic pylsp/pyright; ty itself was never assessed, by anyone, until today.
