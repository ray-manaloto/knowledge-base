The Upgrade Schema

Nine tables. Two hold truth read out of files, four hold judgment rescued from a file being deleted, three hold what happened during a run. Every column here exists because something in the repo would otherwise lose information.

Corrected 2026-08-30: this line read "Eight tables … two, three, three" until a cold review counted the page's own cards. The real set is nine — manifest, dep · probe, watch, watch_review, fork · upgrade_run, stage_event, gate_result. Group 2 always had four.

Why eight and not two

The two-table sketch was not survivable

The original design was dep plus dep_stage. It grew for three reasons, each forced by something real rather than by taste.

You ruled the file gets deleted — “then add the necessary tables to support what would be lost”. currency.toml is not a list of versions; it declares checks, watches, review history and fork state. Those cannot be columns on dep, because they are one-to-many.

A manifest can outnumber its dependency. codex owns two today. So manifests are rows, and the foreign key points from the manifest to the dependency, never the other way.

The authorization gates were being dropped silently. The existing engine has six pre-apply gates that decide whether a bump may proceed. The two-table sketch had nowhere to record their verdicts, which would have quietly removed the safety bar rather than porting it.

The shape

How the eight relate

Group 1 · truth, read out of files

What a dependency is

Neither of these tables owns a version. Both are populated from mise.toml, pyproject.toml and the 97 manifests, and the upgrade task writes new pins back into those files.

dep

one row per dependency · 33 direct today

CREATE TABLE dep (
  name             TEXT PRIMARY KEY,
  kind             TEXT NOT NULL,   -- generated enum: mise | python | manifest_only
  mise_key         TEXT,            -- the [tools] key, when kind='mise'
  python_package   TEXT,            -- the distribution name, when kind='python'
  binary           TEXT,            -- what lands on PATH; often != name
  pypi             TEXT,            -- installable truth for latest
  github           TEXT,            -- owner/repo; narrative only
  tag_prefix       TEXT,            -- 'v' | 'rust-v' | '' — codex needs this
  pin              TEXT,            -- OBSERVED from the file, never authoritative
  latest           TEXT,            -- last resolved upstream version
  latest_checked   TEXT,            -- ISO-8601; a stale latest must be visible
  expected         TEXT,            -- hand-synced fallback where no pin is machine-readable
  source_only      INTEGER NOT NULL DEFAULT 0,
  os_gate          TEXT,            -- e.g. 'macos' — absence is SKIP, never DRIFT
  version_args     TEXT,            -- argv to ask the binary its version
  version_pattern  TEXT,            -- regex pulling the version out of that output
  note             TEXT             -- prose judgment; see the note-splitting rule below
);

The load-bearing column is pin, and it is the one that must never be trusted. It records what the file said when the database was last populated. If it disagrees with the file, the file wins and the row is stale — that direction is the whole design.

latest_checked is not decoration: without it, a latest resolved three weeks ago is indistinguishable from one resolved this morning, and the engine reports “current” on evidence it never re-took.

manifest

one row per sources/*.manifest · 97 today

CREATE TABLE manifest (
  name        TEXT PRIMARY KEY,   -- the file stem
  owner_dep   TEXT REFERENCES dep(name),  -- NULLABLE. see below
  url         TEXT NOT NULL,
  ref         TEXT NOT NULL,      -- 'rust-v0.151.0' or 'main' — different clocks
  commit_sha  TEXT NOT NULL,
  kind        TEXT NOT NULL,      -- generated enum: code | docs
  scope       TEXT,
  build       TEXT NOT NULL,      -- generated enum: include | skip | defer
  reason      TEXT,               -- mandatory when build != 'include'
  note        TEXT
);

owner_dep is nullable on purpose, and that nullability is a finding rather than a convenience. Of the 97 manifests, 35 map to a pinned dependency, 50 are dependency-shaped but unpinned, and 12 are not dependencies at all. A NOT NULL here would force 62 rows to invent an owner.

Why the key is on this table and not on dep. codex owns codex.manifest (ref = rust-v0.151.0, openai/codex) and codex-docs.manifest (ref = main, a different repository). A single syncs_manifest column on the dependency row could hold exactly one of those. Both were read fresh; this is a live one-to-many, not a projected one.

Group 2 · judgment, rescued from the file being deleted

What currency.toml was actually holding

The file has 22 readers and is roughly 85% prose judgment. Deleting it without these four tables would drop behaviour, not just configuration.

probe

one row per declared check

CREATE TABLE probe (
  id          INTEGER PRIMARY KEY,
  dep         TEXT NOT NULL REFERENCES dep(name),
  kind        TEXT NOT NULL,   -- GENERATED enum, see the hedge below
  path        TEXT,
  pattern     TEXT,
  field       TEXT,
  tracks      TEXT,
  expect      TEXT,
  params_json TEXT,           -- the escape hatch, present from day one
  note        TEXT            -- WHY this check exists; often the only record
);

One table rather than seven, because every one of these is the same shape: a declared check, some parameters, and a judgment note. The current extra_probes, backend_probes, ref_binding, docs_watch, artifact, input-glob and skill-stamp constructs all collapse into it. Per-kind validation lives in code, not in the table.

watch

one row per tracked upstream issue

CREATE TABLE watch (
  id     INTEGER PRIMARY KEY,
  dep    TEXT NOT NULL REFERENCES dep(name),
  kind   TEXT NOT NULL,   -- generated enum: issue | local
  ref    TEXT NOT NULL,   -- issue number, or a local identifier
  repo   TEXT,
  note   TEXT            -- the finding itself, not a description of it
);

watch_review

one row per re-probe of a watch · the append-only log

CREATE TABLE watch_review (
  id       INTEGER PRIMARY KEY,
  watch    INTEGER NOT NULL REFERENCES watch(id),
  version  TEXT NOT NULL,   -- WHICH release this was cleared against
  reviewed TEXT NOT NULL,   -- ISO-8601
  method   TEXT NOT NULL,   -- how it was re-probed; recoverable later
  verdict  TEXT NOT NULL,   -- generated enum
  evidence TEXT
);
This table is the answer to the prose question

The advisor previously called losing currency.toml’s prose the most-regretted risk, and proposed a single note column. Re-examined against the real file, that is wrong for half of it: the re-probe history is roughly 900 lines of append-only log wearing a blob’s clothes.

Two things break concretely if it stays a blob. A gate that must answer “cleared against WHICH release?” cannot version-compare free text — a defect this repo has already hit once. And the recorded method of a past probe becomes unfindable, so the next reviewer re-invents it.

So the split is: history becomes rows; condition-carrying rationale stays one note per owning row. “Why sha256 and not stat” is judgment and belongs in prose. “Cleared at 0.9.48 on 12 August by re-reading llm.py” is a record and belongs in a row.

fork

optional · at most one row per dependency

CREATE TABLE fork (
  dep           TEXT PRIMARY KEY REFERENCES dep(name),
  upstream      TEXT NOT NULL,
  base_ref      TEXT NOT NULL,
  base_commit   TEXT NOT NULL,
  pr            TEXT,
  reason        TEXT NOT NULL,
  clears_when   TEXT NOT NULL   -- the condition that retires the fork
);

A table rather than six nullable columns on dep, because these fields are all-or-nothing: a fork without a base_commit or without a clears_when is not a partially-described fork, it is a broken record. A separate table lets the database say so; six nullable columns cannot.

Group 3 · what happened during a run

The state machine’s tables

These three are the runtime. Their enums are the code-generated ones, and a state machine library owns which transitions between them are legal.

upgrade_run

one row per attempt · the DBOS workflow instance

CREATE TABLE upgrade_run (
  id            INTEGER PRIMARY KEY,
  dep           TEXT NOT NULL REFERENCES dep(name),
  from_version  TEXT NOT NULL,
  to_version    TEXT NOT NULL,
  state         TEXT NOT NULL,   -- GENERATED enum; the machine's current node
  batch         TEXT,             -- groups the runs that become one PR
  started       TEXT NOT NULL,
  ended         TEXT
);

stage_event

append-only · current state is derived, never updated in place

CREATE TABLE stage_event (
  id        INTEGER PRIMARY KEY,
  run       INTEGER NOT NULL REFERENCES upgrade_run(id),
  stage     TEXT NOT NULL,   -- GENERATED enum
  state     TEXT NOT NULL,   -- GENERATED enum, incl. skipped_tokens
  manifest  TEXT REFERENCES manifest(name),  -- see the two-clock note
  ts        TEXT NOT NULL,
  evidence  TEXT            -- path to the artifact that settled it
);

Append-only, not update-in-place. pending → running → failed → reverted is the evidence; collapsing it to a current-state column throws away the reason a dependency was rejected the moment it is rejected.

The two-clock problem, and why no enum split is needed

codex’s code manifest follows a release tag; its docs manifest follows another project’s main. One bump cannot advance both, so “source synced” is genuinely two different claims.

The fix is scoping, not a bigger enum: stage_event.manifest is required for the source-facing stages and forbidden for the dependency-level ones. The workflow fans out one sub-run per owned manifest, and the two clocks become two event streams under one run. The state machine is unchanged.

gate_result

one row per authorization gate per run · six per run today

CREATE TABLE gate_result (
  id             INTEGER PRIMARY KEY,
  run            INTEGER NOT NULL REFERENCES upgrade_run(id),
  gate           TEXT NOT NULL,   -- GENERATED enum, from decide.py's six
  verdict        TEXT NOT NULL,   -- pass | ambiguous — never a silent third state
  question       TEXT,             -- what a human was asked, if anything
  detail         TEXT,
  recommendation TEXT,
  answer         TEXT,             -- what the human said
  ts             TEXT NOT NULL
);

This table exists because a cold review found the two-table sketch had nowhere to put it. The existing engine will not apply a bump unless six gates pass, and it fails closed — anything unreadable is ambiguity, not consent. Dropping the table would have dropped the bar with it, invisibly.

The hedge

What will be wrong about this in three months

Named in advance: probe’s parameter union

This repo invented roughly eight distinct probe kinds in six weeks. The ninth will not fit path / pattern / field / tracks / expect, and the tempting fix — add a column — is a migration every time.

The hedge is already in the DDL: params_json ships from day one, and the kind enum plus its per-kind validator are code-generated. A ninth probe kind then becomes a regenerated enum member and a new validator branch, not a schema migration.

That is the general pattern in this schema and it is worth stating once: every enum here is generated, so adding a member is a codegen run rather than a hand-edit — which is exactly what your state-machine requirement asks for, applied beyond the state machine itself.
