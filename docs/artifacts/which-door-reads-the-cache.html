Which door reads the cache

There are two ways into openai-cli extraction. One of them is the route the house ranking calls best. The other is the only one that doesn’t re-buy the whole corpus when a run dies halfway.

Semantic extraction spends real money at a provider. A long run over this corpus is measured in hours, and it will be interrupted — a laptop sleeps, a session ends, a chunk wedges. What decides whether that costs you an inconvenience or the entire bill again is one question:

Does the route you took check what it already paid for, before it pays again?

Both routes write to the same cache. Only one of them reads it.

Why this is uncomfortable

The house ranking for this repo puts the public SDK first and shelling out to the CLI second. That ranking is about coupling — the SDK route cannot drift against private internals, and its backend and model are real function parameters rather than environment variables that can silently come apart. All of that is still true. It is simply not free: on this verb, rank 1 costs you cache resumption and rank 2 keeps it.

So the real question isn’t “how”

It’s which door to open, and the answer decides what gets built:

Open the CLI door

Restore the entry point that was removed, now that its three blocking defects are closed. Keeps cache resumption. Accepts rank 2 and the environment-variable coupling that comes with shelling out.

Open the SDK door

Call the pinned function directly with backend="openai-cli". Honours rank 1, no env coupling possible — and every interrupted run starts from zero until someone builds the cache read that graphify keeps in its CLI layer.

Open the SDK door, and build the missing reader

Rank 1 plus resumption: wrap the pinned call with our own cache check, using the same public function graphify’s CLI calls. More work than either alternative, and it’s our code to maintain — but it is the only option where neither property is given up.
