Aggregated-Research Plugin Blueprint

You asked for everything a Claude Code plugin can bundle, and for the plugin to work like the firecrawl and ctx7 ones. Both were read. The short version: firecrawl is the pattern; the context7 plugin is the opposite shape; and a plugin can carry a lot — but it cannot install your CLI for you.

How the CLI gets onto the machine

No manifest field installs an external CLI — but a hook script can, and the docs show exactly that shape. Corrected 2026-08-28 after your comment "we can have a script that downloads the cli from repo as a github package or artifact" — an earlier version of this section stopped at "cannot". The paths are: bundle a binary under bin/; declare where a tool lives (.mcp.json/.lsp.json command); Node deps auto-install with --ignore-scripts (nothing builds); or a SessionStart hook that installs into ${CLAUDE_PLUGIN_DATA} — the documented answer for "dependencies the automatic install can't provide", a directory that survives plugin updates. plugins-reference.md:718-747, 784-809, 869-870 So the blueprint's hook does not merely check: it fetches the pinned CLI release from GitHub (a wheel or a `uv tool install git+…@tag`) into ${CLAUDE_PLUGIN_DATA} when the recorded version differs, and prints what it did. Firecrawl relies on the user instead (npx firecrawl-cli@latest init; here mise.toml:180 pins npm:firecrawl-cli) — ours goes one step further because you asked it to.

The blueprint

Manifest facts that decide the details

  • No fixed version. "Pushing new commits without bumping it has no effect" — users would go stale; omitting it tracks the git SHA. plugins-reference.md:1300-1320 · plugin-marketplaces.md:922-925
  • Cross-marketplace deps need the root marketplace's allowlist (allowCrossMarketplaceDependenciesOn); trust does not chain. The four names already sit in this repo's extraKnownMarketplaces. plugin-dependencies.md:79-104
  • Tags for semver deps are {plugin}--v{version} via claude plugin tag --push. plugin-dependencies.md:23-49
  • A command plugin source exists (v2.1.229+; installed 2.1.250): a marketplace entry can say {source: "command", command: "aggregated-research claude-plugin-path"} and the CLI generates the plugin directory each session. Tempting; deferred — it needs one-time explicit acceptance and cannot be a transitive dependency. plugin-marketplaces.md:499-561
  • Marketplace prep is the 2026-08-27 decision, unchanged: tag pre-reset-2026-08-27, push it, then wipe main. Today: 0 tags, one plugin, last push 2026-04-08.
The one fork that is yours. Firecrawl and context7 disagree on the interface: CLI through Bash (firecrawl) or MCP tools (context7). The blueprint above is CLI-only, because your words were "a full cli", and because the spine needs file-isolated, machine-readable output that a CLI gives for free. An MCP server can be added later as a thin wrapper over the same CLI if a tool-call interface turns out to matter. Confirm CLI-only, or say MCP too.

Build order, cheapest first

  1. CLI entry point + trackers verb + --json/-o convention + one test that goes red (mostly exists).
  2. Plugin dir in this repo first (dogfood): manifest without version, the spine skill, the SessionStart check, rules/security.md.
  3. Marketplace: tag, reset, manifest entry, allowCrossMarketplaceDependenciesOn; install here from the marketplace; delete the local skill.
  4. packages, codesearch, links, breadth — each prototyped end to end before its verb lands (your standing "prototype all the tools first").
  5. Split the CLI out to its own uv-installable package; pin it in mise.toml beside firecrawl-cli and ctx7.

Every step goes fable-advisor → codex-implementer → cross-family cold review, per your 2026-08-27 rule.
