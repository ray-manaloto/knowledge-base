Two Roads to a Commit

Yes for the half you asked about — and you already built it for the other half, better than the obvious version. The gap is the handoff between them, and all three open tickets live exactly there.

Syncing a source is two questions, not one

They have different right answers, and only one of them is a git question.

“Which version should we be on?” is a release question — it needs to know what is a real release and what is an alpha someone tagged on a Tuesday. Git has no idea. A tag is a tag.

“Which commit is that version?” is an object question — given a name, what does it point at. Git answers this natively; the difficulty is that an annotated tag has two valid answers and the wire protocol makes you infer which is which.

Hop 1 is already right, and more carefully than I'd have written it

Measured against openai/codex, the worst case in the corpus.

$ gh api repos/openai/codex/releases?per_page=6 rust-v0.150.0-alpha.9 prerelease=true rust-v0.150.0-alpha.8 prerelease=true rust-v0.149.1 prerelease=false <- the only real release here rust-v0.149.0-alpha.4.3 prerelease=true rust-v0.150.0-alpha.7 prerelease=true rust-v0.149.0-alpha.7.2 prerelease=true

git ls-remote --tags sees all six as equals — it returns 26 lines over 13 distinct tags for the rust-v0.149.0 prefix alone, twelve of them alphas. Nothing in the git protocol says which is shippable.

And upstream.py:519-533 does not merely call the easy endpoint. Its own comment: “greatest by VERSION order among non-draft, non-prerelease releases — deliberately NOT /releases/latest, which GitHub orders by publish date. That distinction is real: /releases/latest returns rust-v0.149.1 here only because the alphas happen to sort that way, and a backported patch published tomorrow would flip it.

Hop 2 is where gh would actually earn its keep

Both arms probed live. The API states what the protocol makes you infer.

$ gh api repos/agent-sh/agnix/git/ref/tags/v0.50.0 {"sha":"7e168bc4a84c357807b519db2eb103351e545fdb", "type":"tag"} <- ANNOTATED, stated $ gh api repos/agent-sh/agnix/git/tags/7e168bc4a84c357807b519db2eb103351e545fdb {"object":{"sha":"faaeed49b5d018aaadecc2b2d21dcf049ed817c0", "type":"commit"}} $ gh api repos/jdx/hk/git/ref/tags/v1.56.1 <- control arm {"sha":"fdbb35c1cb9d1487e8350a0888877c0d74d4b611", "type":"commit"} <- LIGHTWEIGHT, stated

That single type field is the difference. Every one of the three open tickets exists because the git protocol does not have it:

ticketthe defectwould it exist under gh?
#500 which identity a manifest records, inferred from a ^{} suffix No — type says it outright
#501 two functions inferring differently, so a raw compare is always false No — one stated answer, nothing to diverge
#503 a ref pattern tail-matching sub/v1.0.0 when asked for v1.0.0 No — the ref path is exact and 404s

The 404 arm is worth stating precisely, because the obvious probe does not show it: asking codex for v0.149.0 returns 404 from the API and also returns nothing from git, since v0.149.0 is not a suffix of rust-v0.149.0 at a / boundary. The trap needs a genuine nested name, and the arm that shows it is a local repo holding only sub/v1.0.0 — where git answers a query for v1.0.0 and the API would not.

The bottom three rows are the reason this is a scoping question rather than a straight swap. Two of them are already paid for: all 84 manifests are github.com, and gh is already a hard dependency of the currency engine, of kb-ship and of kb-land. The third — rate limits — is the one that bites, and this repo has already been bitten by it: a rate-limited response parsed through a jq fallback reads as NOT FOUND, which is a wrong answer wearing the costume of a real one.

The recommendation

Do this

Give hop 2 to gh, on the bump path only

currency apply and kb-manifest-add already require gh and already run online. Resolving a version to a commit there via git/ref/tags/{tag} deletes the inference that produced #500, #501 and #503 rather than fixing it — the type is stated, the lookup is exact, and there is no ^{} string to parse.

Do NOT do this

Leave the build path on git

_ensure_clone already has the repository in hand and resolves against it locally — no network, no auth, no rate limit, and correct by construction. A kb-build that needs a GitHub token to reproduce a corpus from committed inputs is a worse build. The precedent is in the tree: sync.py's _tag_commit asks the local clone and gets both identities for free.

One thing to settle before it is built, because it is the failure mode the rate-limit lesson names: a 404 and a 403 must not resolve to the same word. “That tag does not exist” and “we asked too often” are different facts, and a resolver that collapses them will pin the wrong thing quietly. That is the same distinction this repo already draws between DRIFT, SKIP and OK.
