The parked extractor

The next task needs one command. That command was deleted on purpose eight weeks of work ago, under a condition that has since been met and nobody went back to check.

The job in front of us is the mise prose slice: take about twenty-five of mise's markdown files, run them through graphify's openai-cli extraction backend, and see what it costs before committing to the other three hundred.

Every piece of that exists. The fork is pinned and healthy. The backend works. The mise clone is sitting on disk at the right commit. What is missing is smaller and more annoying than any of those: the two lines of wiring that let a person type the command.

What actually happened

On 2026-08-24 a cold review of fa4ed551ac7e found three real defects in the extraction module, all of them reachable only through the mise task and the CLI subcommand. The response was not to leave them open — it was to delete the two entry points, which made every one of the three unreachable by construction while the fixes were written.

That was the right call. Both removal sites still carry the note explaining it, and both name the same restore condition in the same words: restore this branch and the mise task together, and only once those three are closed.

The fixes landed. All three issues are closed. The module now carries seventy tests, four of which drive _run_real and _run_cluster directly — the exact hole #481 was about. The wiring was never put back.

Why this is easy to miss

A removal note is written by the session doing the removing, and read by nobody afterwards. It states its own expiry condition in prose, inside a comment, in two files — and no gate, check, or task ever evaluates whether that condition has come true. The issues closed on a different branch, weeks later, with nothing pointing back.

What restoring it actually is

Two deletions to undo, in one commit, plus the gates. But the removal note is explicit that this is not a repair:

“The module is a stopgap for the SDK path, not the destination — so reviving it is a decision to take, not a repair to perform.”

— the same sentence, in both removal notes

That matters because of a standing call: SDK over CLI, never internals. This module shells out to the graphify binary. The destination is the Python SDK. Un-parking the stopgap buys the slice today and puts a known-temporary path back into daily use.

The alternative is to reach the same backend without the module — which is possible, because --backend is a flag on graphify extract itself. But this repo denies hand-run graphify at the hook, by design, so that route needs its own narrow task rather than a typed command.

The decision

  1. Restore the wiring. Put both lines back, run the gates, and start the slice today. Accepts the stopgap staying in service.
  2. Build the narrow task instead. One task that does only the slice, going straight to the pinned binary, leaving the parked module parked. More work before the slice starts; no stopgap revival.
  3. Go SDK-first. Skip both and drive extraction through graphify's Python SDK, which is where this is meant to end up. Most work, and the slice becomes the vehicle for a larger change.
