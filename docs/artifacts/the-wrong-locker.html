The wrong locker

A plugin was told where its own belongings live. It was told wrong — handed the address of a different plugin's locker. Everything that followed is a consequence of that one bad address.

01

Every plugin gets a private locker

A Claude Code plugin ships small — some markdown, a couple of scripts. Anything heavy it needs (a Python runtime, tools, caches) it installs later, into a private folder of its own. Ours holds about 1.3 GB.

Claude Code names that folder after the plugin: ~/.claude/plugins/data/aggregated-research-ray-manaloto. The codex plugin gets …/codex-openai-codex. Every plugin, its own locker.

02

The plugin is told its address in a note

The plugin's script does not work the address out for itself. Claude Code writes it into an environment variable — CLAUDE_PLUGIN_DATA — on the process it launches for that plugin. The script reads the note and goes there.

That is correct, and documented, for a hook Claude Code runs on the plugin's behalf.

03

Run it any other way and the note is someone else's

Type the command into an ordinary terminal — which is exactly what this round asked for — and the note is still pinned up. But it now carries whichever plugin wrote it last. In this session that was the codex plugin.

04

And it would have built a shelf in there

Refusing to start is the visible half. The script also runs mkdir -p on whatever address the note gives it — so for some subcommands it quietly creates a directory inside the other plugin's locker.

Measured against the pre-fix wrapper: it created a folder named some-other-plugin inside a foreign data root. The patched one creates only its own.
05

The fix: read the name on the locker

Don't trust the note blindly. Work out the plugin's own address, and accept the note only when it points at a locker whose name is ours. Anything else — another plugin, a relative path, a name that merely ends in ours — is ignored and the known-good address is used instead.

Why honour the note at all, then? So that if Claude Code ever moves where lockers live, the plugin follows. It checks the name, not the neighbourhood.
06

The part worth your attention: my test could not fail

I added a check to catch this in CI. A cold reviewer found the check was decorative — it read the wrong number, and always read “fine”.

what I wrote
if ! cmd; then
    rc=$?
fi

Inside the branch, $? is the result of the test — “did the negation succeed” — which is always 0. The failing command's real code is already gone.

what it had to be
cmd || rc=$?

Here $? is still the command's own code.

The shape to notice. The bug I set out to fix was “a check that reports success no matter what.” My fix for it was a check that reports success no matter what. Same defect, one layer down — which is why the fix commit gets its own cold review rather than riding along on the first one's.
