Two SHAs, One Tag

An annotated git tag names two objects, and this repo already knows that in two places. The ticket that says otherwise sends the fix in the wrong direction — while the defect that is actually live sits in five manifests, silently, and has for weeks.

Three claims, checked

All three probed against the live remotes and the installed source this session.

Refuted

“--refs strips the peeled line.” It does not — not here. git ls-remote --tags --refs <url> v0.50.0 and the same command without --refs return byte-identical output. The peeled entry is named v0.50.0^{}, so the ref pattern never matched it in the first place.

A fix that only removes --refs changes nothing, and would pass its own test.

Refuted

“The tag-object SHA corrupts the reproducibility contract.” kb-build peels before it verifies, deliberately, and says so: “The pin may be either a commit object or an annotated-tag object. Both legitimately peel to one commit/tree.” graph.py:640-642. The currency check accepts both for the same reason sync.py:1633-1645, #246.

Live

The defect runs the other way, and it is older and wider than the ticket. latest_commit() returns the tag object, but five manifests record the peeled commit — so latest == m.commit graph.py:3276 is permanently false on five sources that have not moved. Three of the five predate last round entirely.

Corrected after publication

The first version of this page said the phantom-advance defect affected two sources and that last round created it. A full audit of all 84 manifests, run after publishing, refutes both halves: it affects five, and codex, ffmpeg and mise were already peeled before that round began. The round added two to an existing population; it did not start it. The audit table below is the evidence.

What an annotated tag actually is

The mechanism the whole disagreement rests on.

A lightweight tag is a name pointing straight at a commit — one name, one SHA, no ambiguity. An annotated tag inserts a real object in between: a tag object carrying the tagger, the date and the message, which in turn points at the commit. Two objects, two SHAs, one release.

The probe, both arms

Run against the live remotes this session. The middle pair is the one that matters.

$ git ls-remote --tags --refs https://github.com/agent-sh/agnix v0.50.0 7e168bc4a84c357807b519db2eb103351e545fdb refs/tags/v0.50.0 $ git ls-remote --tags https://github.com/agent-sh/agnix v0.50.0 7e168bc4a84c357807b519db2eb103351e545fdb refs/tags/v0.50.0 ← identical. --refs changed nothing. $ git ls-remote --tags https://github.com/agent-sh/agnix 'v0.50.0*' 7e168bc4a84c357807b519db2eb103351e545fdb refs/tags/v0.50.0 faaeed49b5d018aaadecc2b2d21dcf049ed817c0 refs/tags/v0.50.0^{} ← there it is: the PATTERN was the bound.

So the mechanism is not the flag. _tag_candidates() builds exact ref names manifest.py:235-243, and an exact name can never match v0.50.0^{}. That is a spelling bound, not a stripped line — and the docstring at manifest.py:253 asserts the opposite.

Who reads the pin, and what each one does with it

Every consumer of a manifest’s commit field in kb_setup. Only one compares it raw.

What a phantom advance looks like

It is not loud. mise run kb-update -- agnix prints faaeed49 -> 7e168bc4 as though upstream had moved, writes the tag object over the recorded commit, re-clones and re-runs a full AST extraction — for a source that never moved. The manifest silently flips convention, and nothing reports that it did. Repeat on codex, ffmpeg, mise and rumdl.

Two things follow. The wasted rebuild is the cheap half. The expensive half is that kb-update can never answer “has this source moved?” for those five — it says yes every time, so the one question it exists to answer is dead for the sources where a version bump matters most.

So the real question is a convention, not a bug

Both are internally consistent. Only one is consistent with what the repo already does.

Record the tag object

What the writers emit

  • Matches latest_commit() and resolve_tag() as written, so the compare holds with no code change.
  • Matches the note at sync.py:1636-1639 — “what kb-manifest-add therefore records.”
  • But: makes a field named commit hold a non-commit, and only on tag sources — branch sources keep storing real commits.
  • Costs: migrate 5 manifests backwards, away from the identity a human would verify by hand.
Record the peeled commit

What the majority already holds

  • 5 of 9 annotated manifests are already peeled, three of them long before this round — this is the incumbent, not the proposal.
  • commit then means one thing on every source, tag-pinned or branch-pinned.
  • Requires latest_commit() and resolve_tag() to peel — sharing one helper, or they drift again.
  • Costs: two functions, 4 manifests migrated, and a real annotated-tag fixture.

One change is unconditional and independent of the choice: latest_commit() and resolve_tag() must return the same identity, from one code path. They agree only by accident today — both happen to read ls-remote’s unpeeled line — and nothing in the suite asserts it. Every existing resolve_tag test fakes the remote tests/test_manifest_add.py:64, so no test has ever seen a real annotated tag, and 16 of the 25 tag-pinned sources could not have exposed it in production either.
