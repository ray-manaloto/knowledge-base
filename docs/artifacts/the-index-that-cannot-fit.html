The Index That Cannot Fit

339 memories. An index that holds 249 of them. Listing every one at today's writing style would take ~95 KB against a 24.4 KB ceiling — so every compaction sheds entries, and they vanish rather than shorten.

This is not a tidiness problem. The arithmetic makes a complete index impossible, which means the file has been quietly making a decision nobody wrote down: which memories stop being reachable.

The arithmetic

Four numbers, all measured this session. Only one of them is a choice.

Why the best answer is currently the wrong one

Offloading the tail into the graph is the right architecture: auto-memory costs context in every session, the graph costs nothing until queried, and the split is exactly what the two stores were built for. It is blocked on one measured fact — 0 of 271 work-memory files are reachable from the graph. Pointing the index there would make the tail look reachable while being less findable than a grep is today.

The acceptance test is not "the write succeeded". It is a control-armed read: a kb-query returns a fact recorded by kb-remember, and the same query shape returns nothing for a fact never recorded.

The pattern worth taking away

Both breaks here — this one and #212 — have the same shape: a write path with no read path. Every observable is green. The file lands, the commit includes it, the aggregate regenerates. Nothing in the loop ever asks the question the loop exists to answer, so the absence is invisible from inside it.

Worth asking of every loop in this repo whose success criterion is "the artifact was written".
