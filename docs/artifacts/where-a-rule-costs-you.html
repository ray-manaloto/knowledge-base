Where a Rule Costs You

You asked whether "use the LSP, not grep, for callers" should be a path-filtered rule instead of memory — and which option spends the fewest tokens. Neither rule form is right here, and the reason is specific to how this session actually reads files.

Corrected 2026-08-25, after publication — the docs were fetched and three claims here were wrong

1. Progressive disclosure via subdirectory CLAUDE.md is REAL, and this page did not consider it. The docs say it plainly: "Claude also discovers CLAUDE.md and CLAUDE.local.md files in subdirectories under your current working directory. Instead of loading them at launch, they are included when Claude reads files in those subdirectories."

2. The "front-loaded, not bounded" cost claim was too strong. On compaction the docs say "Nested CLAUDE.md files in subdirectories and rules with paths: frontmatter reload as Claude reads files they apply to" — so on-demand instructions drop at compaction and return only on a fresh match. That is a better cost profile than the figure below draws.

3. AGENTS.md is NOT loaded and should never have been in the byte table. "Claude Code reads CLAUDE.md, not AGENTS.md." This repo has no @AGENTS.md import, so its 2,369 bytes cost nothing. The always-loaded total is ≈185,000, not 187,500.

What survives: the recommendation. Rules with paths: do trigger "when Claude reads files matching the pattern, not on every tool use", so the Bash-first concern below still stands — and it is now measurable rather than argued, via the InstructionsLoaded hook the docs provide for exactly this.

Short answer: a sixth hook guard. It costs zero context tokens until someone breaks the rule, the chain it joins already exists and is tested, and this repo has measured that a deny changes behaviour where a warning does not — 62 violations → 0, against 0 compliance in 19 chances for the warning it replaced.

The three mechanisms, and when each spends

Context cost is not one number — it depends on when the text enters the window. That is the whole comparison.

Why the path filter would not fire here

This session is told to read Python with cat and sed, not the Read tool

A path-scoped rule triggers when Claude reads a file matching the glob. But the standing instruction in this session is to do file work through Bash wherever it can — cat, head, sed -n — and to fall back to the Read tool only when Bash cannot do the job.

So a **/*.py filter would sit dark through exactly the sessions it exists to govern. That is not hypothetical: every Python file I opened while getting this wrong today was opened with sed -n or grep, not Read.

Stated honestly: I have not independently probed whether a Bash cat counts as a read for trigger purposes. This rests on the repo's own recorded reading of the docs, and it is the direction I would bet on — but it is a claim worth one probe before anyone builds on it.

There is a second, older reason, and this repo has paid for it four separate times. A rule whose trigger is an action — about to dismiss a warning, about to stage, about to shell out to an AI CLI, about to claim who calls something — cannot be predicted by any glob. Four rules here carry a written note saying they were path-scoped once, went dark in exactly the sessions that needed them, and were made eager on purpose.

"Who calls X?" is an action trigger. The moment is when a callers claim is about to be made, not when a file is opened.

The three options, priced

Another eager rule

every session · every turn

Joins the 20 eager rules already loading 137,349 bytes — roughly 34k tokens — into every session before you type anything.

Always present, always correct, and the most expensive place to put anything.

A path-scoped rule

zero, then full · if it fires

Free until a matching file is read. Then resident for the rest of the session, same as eager.

And here it likely never fires, because this session reads Python through Bash.

A sixth hook guard

zero until violated

Never enters the context window. Emits a short denial naming the LSP call, only when a caller-shaped grep is actually attempted.

Joins a chain that already exists, is already wired, and already has a test file per guard.

What the guard would actually do

Narrow on purpose. Every measured defect in this repo's guards has been a false positive, never an evasion — so the design bias is precision.

Deny: a repo-wide or directory-wide search whose pattern looks like a symbol-reference query over Python — a bare identifier, or one followed by ( — and print the exact LSP findReferences / incomingCalls call to run instead.

Never deny: a search scoped to one named file; a search for a string literal, a config key, or prose; anything outside Python; and any command already routed through a mise run kb- task. Same tokeniser the existing guards share, so a quoted commit message containing the pattern is one token and can never sit at a command position.

Cost to build: one module beside the other five, one test file, one row in the redirect table — the shape this repo's own extension note already prescribes.
