The hook is not the bug

Two completely different things happened, at two different places in the chain, and they got tangled together. Here they are, pulled apart.

First: the forked graphify works

You asked to just run it on a simple file. Done — and it worked:

exit code 0

45 nodes, 67 edges, 12 communities written from two source files.

Real run through the forked CLI, with --backend openai-cli on the command line. Nothing mocked.

So graphify is fine. The fork is fine. The install is fine. Whatever is broken is somewhere narrower than “graphify”.

So why is the hook there at all?

It isn’t a safety rail against graphify. It’s a redirect, and it says so in its own words:

Do not run `graphify extract` by hand. Use the mise task: mise run kb-build. All graphify work goes through a mise task.

The reason is that running it by hand skips three things the task does for you: it pins which graphify version actually ran, it strips every non-Claude provider key out of the environment, and it points the output somewhere that isn’t your real graph. A hand-run command silently gets none of that.

The part worth remembering

It blocks typing, not running. Reading commands are never blocked at all — query, explain, path, --version all pass straight through. It only stops the handful of commands that write.

Now the actual bug

When there is prose to read, graphify calls codex. Before doing that it tries to be tidy: it turns off your MCP servers, so extraction doesn’t boot ten of them for a job that calls no tools.

To do that it asks codex “what servers do you have?” — gets ten — and passes back ten switch-off instructions.

One bad name spoils the whole file. So every prose extraction dies in about three seconds, before spending anything.

How I know that’s the cause

Same command, same everything, run twice — only the list of names changed:

names sentresult
the 5 that exist in a configrc 0works
the 5 that don’trc 1invalid transport

Both arms outside graphify, driving codex directly — so the split isolates the cause rather than restating the symptom.

Something I got wrong first

My first attempt at this test reported the failing combination as passing. It hadn’t — I wrote the flag list into a shell variable, and this shell hands that to a command as one long argument instead of twenty separate ones, so none of the switches applied. The test looked clean because it tested nothing. Written properly, the answer reversed.

Where that leaves us

Not broken

The forked graphify. Your codex install. The hook. Code extraction. The whole existing pipeline.

Broken

One tidy-up step inside the fork’s own openai-cli patch — it doesn’t check whether the servers it’s switching off actually exist. It only ever ran with the Claude backend before, so nothing had exercised this path.

The fix is small and it’s in our fork: send a switch-off only for a server that is really there. Everything downstream of that — including the cache question from the other page — is waiting on this one line.
