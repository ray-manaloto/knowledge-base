Owed, and live right now

Why the pinned clone keeps drifting

The session-start check reports that sources/graphify/ sits at b2cd3626 while its manifest pins cdfb11c0. That is not someone forgetting to reset a directory — it is a structural consequence of how a frozen manifest resolves its clone path.

A manifest can be frozen to a commit, but its directory is computed from the source's name alone. So two different pins of the same source resolve to the same folder on disk, and the checkout happens in place.

Manual reset until then: git -C sources/graphify checkout -q cdfb11c000ccbe3af1fbd1b9c41ab42718d54fc8

The documented apply command silently does nothing

The tool-currency skill does name apply. Step 4 of its own procedure, in a runnable bash fence at SKILL.md:86:

mise run kb-currency -- --tool <name> apply

That command runs the report and discards the word apply. It exits 0, writes another page under docs/currency/, and edits no pin — indistinguishable from success to anyone following the documented steps.

So the work is not "run the updates" — it is closing that column and the seams after it, so one invocation carries a tool from drift-detected to graph-rebuilt. The agent's only remaining job is the amber cell: read the release notes and judge what affects this project. And a fix here must include the arm that would have caught this one: a documented command that exits 0 while doing nothing is the failure mode to test for.

And even reached, apply serves 8 of 15 tools

Wiring a task to apply would still not automate the two tools that are drifting right now. apply knows exactly one pin format — a [tools] entry in mise.toml — and seven of the fifteen configured tools are pinned somewhere else.

Three more findings from the same inventory shape the build, each cited in the lane report at .agent/kb/reports/agents/2026-08-24-pipeline-inventory/:

  • apply ignores ref_binding. currency.toml binds three files to graphify's manifest ref; sync detects their drift and apply never moves them, so they stay hand-edited.
  • apply discards the verdict a human just approved and re-runs the full network probe. An upstream blip between the interview and the apply turns an authorized bump into an ambiguity.
  • Manifests have two writers with different semantics. write_commit (used by kb-update) moves commit to upstream HEAD and leaves ref alone; write_pin (used by apply) moves both to a resolved tag. Nothing reconciles them, so a kb-update can leave commit off the tag its own ref names.

The graph can't answer, and rebuilding won't fix it

Querying this repo's own code from the graph fails constantly, and the instinct is to rebuild. Measured, the problem is not staleness — it is dilution and coverage, and a rebuild changes neither.

And the blocker in front of a rebuild is stale. kb-currency-check reports every session that a build ran and failed on .agent/skills/blocking-io-guard/templates/anchor.template.py, and predicts "re-running will fail again". Asked in the margin

Why the orchestration flow never fires

It is gated by its own first clause. The trigger in .claude/CLAUDE.md line 31 begins:

When the session model is Fable, without being reminded: non-trivial implementation runs the fable-orchestrator architect-as-orchestrator flow…

This session's model is Opus 5, and Opus is the repo's documented default. The condition is false, so the standing instruction does nothing — every session here has been in that state since the line was written.

That gate is not a mistake in our config; it is the plugin's intended design. Its own changelog says the canonical trigger "now begins 'When the session model is Fable' — sessions on other models skip the flow instead of running an architect pattern their model wasn't chosen for", and its setup wizard writes that gated form. An unconditional trigger is a shape the wizard recognises and offers to upgrade away from.

So there are two honest ways to arm it, and they are not equivalent: switch the session to Fable 5 and run the pattern as designed, or remove the gate from line 31 so it fires on Opus too — accepting that the architect is then a model the plugin did not pick for the role. Invoking /fable-orchestrator:orchestration by hand, as this session did, works either way and is what the plugin documents for anyone without the always-on line.
