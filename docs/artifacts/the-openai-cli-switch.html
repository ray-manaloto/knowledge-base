The openai-cli switch

The question is smaller than the handoff framed it

The handoff says any image in the corpus must “stay on claude-cli, be skipped explicitly, or route elsewhere.” There is a fourth option, and graphify already implements it: a non-vision backend gets the pixels stripped and the image still becomes a graph node, described by its path instead of its contents.

So nothing breaks and nothing is dropped. What changes is that an image goes from SEEN to NAMED — a real loss of fidelity, but a graceful one, and reversible by re-extracting on claude-cli later.

The chunk probe is control-armed: the same grep shape finds a .md source in 27 of 27 chunks and an image in 0, so the zero is an absence rather than a broken pattern.

What this does not establish: that a future detect run would classify none of those 1,289 as extractable. Answering that means running detect, and kb-build is currently failing its preflight (#491) — so the honest bound is the history, not a forecast.

The actual work: three coupled constants

The figure is kept rather than redrawn, because the trap it shows is the reason the fix has the shape it does — and because someone may have acted on the original.

The plan’s finding 7 says kb_setup “passes NO backend anywhere”. It did — and switching it was not one edit.

Two things that are already fine

  • No API key needed. openai-cli is exempted alongside bedrock and claude-cli from the key check — llm.py:2147.
  • clean_env() will not strip the new variables. Its _STRIP_BACKEND_ENV is 19 fixed names and 0 of them are GRAPHIFY_* (graphify_env.py:32–58), so GRAPHIFY_OPENAI_CLI_MODEL survives it. Control-armed: the same grep finds GEMINI, so the zero discriminates.

What actually shipped

Both guards, on the reading that the loss is a degrade and not a break. backend_probes in currency.toml reports DRIFT at session start if a declared backend vanishes from graphify’s table; _refuse_backend refuses at the moment of spend, and does so before the dry run, because a preview of a run that cannot happen is worse than no preview. The default stayed claude-cli — a default that had to be opted out of would put an irreversible spending decision one typo away.

One measurement that shaped the fix and is easy to get wrong: openai-cli declares a model_env_key in the table and claude-cli declares none — while graphify plainly reads one for it at llm.py:1776. So a table-only lookup returns nothing for the default backend, and a shape-only derivation guesses past a backend that names its variable differently. The shipped code derives, then refuses if the table disagrees.

One thing to read, not re-derive

graphify ships its own BACKENDS table at sources/graphify/graphify/llm.py:206–231, carrying each backend’s default model, model env key, pricing and vision flag. Read it rather than hand-rolling a second copy — a second table is how #245 half-landed and how #499 stayed invisible.

Worth knowing while reading it: the openai-cli entry is a patch this fork carries, not upstream. Its own comment warns that if an upgrade removes it, the backend disappears silently and extraction can fall back to the metered OpenAI API — a spending regression.
